The Point of
No Return

Process reward models don't beat outcome-only RL because the reward is denser. They beat it when the environment is irreversible — when the mistake at step 3 dooms a trajectory whose outcome reward doesn't arrive until step 12. That predicts a curve nobody has plotted.

01 The claim

Density is not the mechanism

The standard story for process reward models is that sparse outcome rewards are hard to learn from, so scoring each step gives the optimizer more to work with. That story is true and mostly uninformative — it predicts PRMs help everywhere, which is not what practitioners observe.

Here is a sharper story. Outcome-only RL is fine as long as a trajectory that goes wrong at step 3 can still be rescued by step 12. The final reward is then a fair verdict on the whole policy, and the credit assignment problem is merely statistical — run more rollouts and it washes out. What outcome-only RL cannot handle is a trajectory that became unwinnable at step 3 and spent nine more steps generating tokens that were, in the technical sense, meaningless. Every one of those tokens gets the same negative advantage as the one that actually killed the run.

Process supervision is a hedge against irreversibility. Its value should scale with the fraction of trajectories that die before their outcome is observed — and vanish when the agent can undo.

That is a falsifiable prediction with a free parameter you can control experimentally. If you can build an environment whose recoverability you dial, you can measure the advantage as a function of it. If the curve is flat, the density story wins and the irreversibility story is wrong. If it decays to zero as recoverability rises, you have explained a folk belief and given people a rule for when to pay for a teacher.

Nobody has plotted that curve because nobody builds environments with a recoverability knob. Everything from SWE-bench to WebArena resets clean. That gap is the opening.

02 The task

Irreversible engineering

Real operations work is not a sandbox. Dropping a column deletes data. git reset --hard discards the working tree. A botched backfill is a Tuesday with no undo. Benchmarks have systematically excluded exactly the property that makes the work hard.

The environment family: a container holding a repository, a populated Postgres instance, and a test suite. The task is a migration that genuinely requires destructive DDL — split a table, rename-and-backfill a column, collapse a polymorphic association, drop a deprecated index that a query planner still depends on.

Success

Two conditions, both machine-checked

The test suite passes and a row-level integrity check confirms no data was lost. Both are ordinary Python. There is no judge in the outcome reward — that is the point, because the judge is the treatment.

Irreversibility

An undo tool with budget K

Restores the last snapshot — overlayfs for the filesystem, PITR or a dump for the database. K=0 is a production console at 2am. K=∞ is every RL environment ever published. Sweep K ∈ {0,1,2,4,∞}.

The instrumentation that makes it a paper

After every step, run an automated recoverability oracle: is the target state still reachable from the current state? Concretely — is every pre-migration row still derivable from the live database plus the working tree plus the snapshots the agent has left itself? This is a decidable question over the environment state, not a model judgement.

That gives you, for every trajectory, the point of no return: the step index at which it became unsalvageable. Almost no agentic RL work has this measurement, and it is what converts "the PRM helped" into "the PRM helped because it moved the death step later, or removed it."

03 The dial

What the hypothesis actually predicts

The prediction is not hand-waving — it falls out of a two-line model. If each step independently has hazard h of causing unrecoverable damage, a trajectory of horizon H survives if the number of hazards it hits is within its undo budget K.

So success ≈ base · P(Binomial(H, h) ≤ K). Process supervision doesn't make the agent smarter at the end; it lowers the hazard rate, h → h(1−r). The advantage is the gap between two binomial tails — large when K is small, vanishing as K grows past the expected hazard count.

Push h to zero and the advantage disappears because there is nothing to save; push K past H·h and it disappears because the agent saves itself. Both limbs matter — a null result at low hazard is not evidence against the hypothesis, which is why the sweep has to cover the corner where the effect should be largest.

Two consequences worth stating before you run anything. First, the effect is predicted to be large at K=0 and zero at K=∞, so a single-point comparison at either end is uninformative about the mechanism — the shape is the result. Second, the model says the crossover sits near K ≈ H·h, which means you should report the hazard rate of your environment or nobody can transfer your conclusion to theirs. That is a small methodological ask that the field currently never satisfies.

04 Method

Three decisions that determine whether this works

Where to score — the channel tokens are free segmentation

Glimmer emits <thought>, <action> and <observation> as vocabulary items, with XML-style ATEM tool calls rather than JSON. Step boundaries are therefore declared by the model, not recovered by a heuristic chunker. Score at <action> boundaries and you get an unambiguous, reproducible segmentation for free.

The corresponding masking discipline: <observation> spans are environment-generated and must be excluded from the loss entirely. Training on them teaches the model to predict tool output — useless at best, and a leakage path at worst.

How to shape — potential-based, or not at all

Use Spark's step scores as a potential function: the shaping reward is Φ(st+1) − Φ(st), not the raw score. Potential-based shaping is policy-invariant (Ng, Harada & Russell, 1999) — it can change how fast you learn but provably cannot change what you learn toward. Raw per-step scores have no such guarantee, and the failure mode is specific and predictable:

The predicted hack. A critic reading a trajectory sees a confident, well-structured <thought> and scores the step highly — before the action executes. Optimize that directly and you get an agent that narrates beautifully and acts badly. Run both shapings and show the divergence; it is cheap, and it is the single most useful thing you can hand a practitioner.

# reward assembly, per trajectory
r_outcome = tests_pass(env) and rows_intact(env)      # terminal, verifiable
phi       = [spark_score(prefix_t) for t in action_bounds]  # teacher potential
shaping   = [phi[t+1] - phi[t] for t in range(len(phi)-1)]
# telescopes to phi[-1] - phi[0]: policy-invariant by construction
r_t       = gamma * shaping[t] if t < T-1 else r_outcome

What to score with — distil the teacher, and make that the third contribution

Do the arithmetic before committing. Ten action boundaries per rollout, 32k rollouts per run, ~8k tokens of context per scoring call is billions of teacher input tokens per run. Spark in the inner loop is not viable, and pretending otherwise is how this project dies in week two.

The fix is also the most practically valuable result in the post. Label a subset with Spark, train a small critic on those labels — an 8B model, or a value head on frozen Glimmer — and run RL against the distilled critic. Then plot downstream RL performance against the number of Spark labels. "How many teacher labels before the cheap critic is as good as the expensive one?" is the question every team with an API budget actually has, and the curve is not published anywhere.

05 Teacher cost

The baseline that decides whether anyone believes you

A PRM is not free, so "PRM beats outcome-only at equal steps" is not a result. The honest comparison gives outcome-only RL the teacher's budget to spend on more rollouts. Most published PRM work skips this. Doing it is the cheapest credibility you will ever buy.

The random-critic control deserves emphasis. Shaped rewards change the entropy and scale of the advantage distribution, and that alone can move results. Several published RL gains have evaporated under exactly this control. Running it costs one arm and immunises the whole post.

07 Stack

Don't build the trainer

Every component of this except the environment and the shaping rule already exists in open source, is maintained by people who do this full time, and is more correct than what you would write in three weeks. Build the two novel pieces; borrow everything else.

prime-rl
trainer		 Fully async distributed RL, first-class verifiers support, FSDP + LoRA, split trainer / inference / orchestrator. Recently grew an explicit Algorithms layer for credit assignment. That Algorithms layer — rollouts+rewards → advantages — is the natural insertion point for potential-based shaping. Cleanest place to put our one novel training change. The layer currently answers only "what per-token signal does a finalised rollout produce"; per-turn potentials are an extension, not a config flag.
verl-agent

The closest existing thing to step-level credit assignment in agentic RL. Read it before writing your own advantage estimator. veRL's config surface is heavy, and the env abstraction is less container-native than Harbor's.
Agent Lightning · rLLM
alternative		 Train-any-agent frameworks that sit beside an existing agent harness rather than replacing it. Useful if you want to keep an off-the-shelf agent loop untouched and only supply rewards. Less control over exactly where advantages land, which is the thing we're studying.

The recommendation

Harbor for the environment, SkyRL for training, verifiers as the second target. Our tasks are literally Dockerfile + instruction + test, the SkyRL↔Harbor path is the maintained one for long-horizon container agents, and it means the only infrastructure we write is the part that is actually new: the snapshot/undo tool, the recoverability oracle, and the shaping rule. Package the environment against the verifiers API as well — it is a thin adapter, and Environments Hub distribution is how the artifact outlives the blog post.

Everyone's gap is the same gap. Per-turn credit assignment is not a solved feature in any of these — prime-rl's algorithms layer is per-token over a finalised rollout, verifiers rubrics are per-rollout scalars, SkyRL concatenates turns with masks. The literature is ahead of the frameworks here (GiGPO, MT-GRPO, TCPO all propose turn-level advantage constructions). Our potential-based version is a genuine, small, publishable extension — and the fact that it doesn't exist as a flag anywhere is itself worth a paragraph in the post.

Drop QLoRA for the training arm. The 4-bit setup makes sense for single-GPU fine-tuning, but these frameworks shard bf16 weights over FSDP and don't expect a quantised base. Glimmer is dense 29.6B — bf16 weights shard comfortably across 8×H100 with LoRA adapters. Keep 4-bit for inference-side experiments only.

08 Azure

What to provision, and in what order

Training

One ND H100 v5 node (8×H100 80GB). Split it: ~4 GPUs serving rollouts under vLLM, ~4 training. Glimmer is dense, so every rollout token costs full compute — there is no MoE discount. Rollout generation, not backprop, is the bottleneck, and long agentic traces make it worse.

Environments

A separate CPU VM or AKS pool running the destructive containers, snapshotted via overlayfs. Never on the training host. Budget more environment parallelism than feels necessary — a Postgres migration plus test suite is seconds of wall-clock per step, and it will pin your rollout throughput long before the GPUs do.

Teacher

Check the Foundry catalog for Spark first. Meta announced the 1.2 weights are coming but has published neither date nor licence, so plan for an API endpoint during the labelling phase and switch to the distilled critic for the RL loop. Cache aggressively — trajectory prefixes are shared, and scoring is prefix-heavy.

Staging

Run the two endpoints — K=0 and K=∞ — at small scale before the sweep. If the gap doesn't appear where the model says it should be largest, it isn't there, and you have spent a few hundred dollars finding out instead of a few thousand.

Rough order of operations: week 1, environment + oracle + a handful of hand-written migration tasks, validated by running a stock agent through them and eyeballing where trajectories die. Week 2, the K=0 vs K=∞ pilot. Week 3, the sweep and the compute-matched arm. Week 4, distillation curve and write-up. The environment is the long pole and the reusable artifact — start there, and resist the urge to start with the trainer because the trainer is the fun part.

09 The pre-registration

If the curve is flat, publish anyway

Decide this now, in writing, before any GPU is provisioned — because the framing has to survive both outcomes, and a framing chosen after seeing the result is worth nothing.

"At 30B, a frontier process reward model does not beat compute-matched outcome-only RL on long-horizon agentic tasks, and here is the controlled irreversibility sweep showing where we looked" is a genuinely useful post. The field's current position on when PRMs pay is folklore; a clean negative with a compute-matched baseline and a mechanism knob is more informative than most positives.

And the two artifacts stand either way: an environment family with a recoverability dial, and per-trajectory point-of-no-return instrumentation. Those get reused whichever way the curve goes. That is the test of whether a research post was worth writing — not whether the number went up, but whether the thing you built to measure it is still useful when it didn't.

The sweep reproduces the predicted shape

sim/sweep.py drives the real environment with a scripted agent that hits a destructive action with probability h per step and spends an undo if it has one. "Process supervision" is modelled as a lower hazard. No model, no teacher, no GPU — the point is to exercise the measurement before paying for one.

Large advantage at small budgets, exactly zero when the agent can always undo. This is evidence that the harness measures what it claims to — not evidence about process reward models, since the "supervision" here is a hand-set hazard rate rather than a critic.

Two things the table gets wrong, kept rather than tidied. K=0 and K=1 are not separated at n=40 (standard error ≈ 0.08) — only the decay across the sweep is meaningful. And K=4 misses the analytic curve by 6 points, which is not noise: every undo adds two steps to the episode, and those steps carry their own hazard. Spending budget lengthens the horizon, which creates more chances to need budget. The fixed-horizon binomial model can't see that. If the same signature appears with a real policy it's a finding, not an artefact.

What's in the box

The oracle keeps two strictnesses on purpose. Integrity — the outcome reward — reads the live database only. Recoverability reads the database, the working tree, and any snapshot still within budget. A CSV the agent dumped counts as recoverable but not as a completed migration.

Adapters do the turn → token expansion that no framework provides: per-turn potentials → shaped return-to-go → group-relative advantages → broadcast over <action> spans only, with observation tokens masked. Plain lists, so it drops into whichever trainer wins. The verifiers adapter uses StatefulToolEnv to inject the sandbox handle and hide it from the model's tool schema.

The training loop is deliberately absent — that's SkyRL's or prime-rl's job, and adapters/ is the seam. SparkCritic refuses to run without an API key.
