The thesis

One base model, three deliberate paths

Olmo 3 is organized as a flow: a base-training spine (pretrain → midtrain → long-context) and three post-training tracks that branch off it. Think is the flagship reasoning model (32K-token thinking budget). Instruct trades thinking for latency and function calling — and is warm-started from the Think SFT checkpoint (+3.3 avg). RL-Zero runs RL directly on the base model as a decontaminated science benchmark. Every box below is a released checkpoint plus released data. Click any stage.

Orientation

Two repos, one seam

OLMo-core defines the model and owns pretraining: a config-driven Transformer, FSDP2/HSDP + context parallelism, float8, and a callback-based Trainer that reads pre-tokenized memory-mapped .npy token streams. open-instruct owns post-training: SFT, DPO, and GRPO-style RL over HuggingFace-format models, with vLLM for rollouts and Ray for orchestration. The seam between them is a checkpoint converter (olmo_core.nn.hf.convert) plus a numpy exporter, so a model can round-trip: OLMo-core pretrain → HF for RL in open-instruct → back if needed.

Model architecture

A Llama that traded mystery for stability

Olmo 3 is a dense decoder-only transformer that is deliberately boring in shape and distinctive in the details that matter for training stability. Two signatures inherited from OLMo 2: reordered norm — RMSNorm is applied to each sublayer's output inside the residual (h = x + norm(attn(x))) instead of Llama's pre-norm — and QK-norm, an RMSNorm on the full Q and K projections before RoPE. Both exist to kill loss spikes at trillion-token scale, alongside z-loss (1e-5), fp32 norms with eps 1e-6, and a spike-skipping optimizer (SkipStepAdamW).

What Olmo 3 adds is the attention pattern: sliding-window attention (window 4096) on 3 of every 4 layers, full attention on every 4th and always on the last. Long context comes almost free: YaRN (×8) is applied only to the full-attention layers — the sliding-window layers never see positions beyond their window, so their RoPE is left untouched. 8K context becomes 65K with a 50–100B-token extension stage.

What to steal from the training recipes

The official scripts (src/scripts/official/OLMo3/) read like a staged curriculum: pretrain 5.9T tokens with cosine LR (3e-4 at 7B, 6e-4 at 32B, batch 4–8M tokens); midtrain 100B tokens of high-quality/synthetic data starting from wherever the cosine left the LR, decaying linearly to zero; long-context at seq 65,536 with 8-way context parallelism and best-fit document packing. The 32B midtrain is a soup — two 100B runs with different data-order seeds, parameter-averaged (+2.9 on math cluster). Souping recurs everywhere in this stack: SFT merges two learning rates, long-context merges the last three checkpoints.

The data pipeline

One module, three schemas, aggressive caching

Everything in open-instruct's data path funnels through a single 2,300-line module: dataset_transformation.py. Its design goals, per its own header: handle mixing, handle multiple tokenization schemes, and never tokenize twice — the motivating war story is 32 nodes idling for 21 hours re-tokenizing a dataset. A mix is a list of (dataset, weight) pairs; each dataset flows through a registry of named transform functions; and the result is cached under a content hash that covers the dataset commit, the transform args, the tokenizer files, and the rendered chat template. Change any of them and the cache key changes.

Loss masking is character-offset based: render the whole conversation, then unmask only tokens overlapping assistant-content spans. All assistant turns train; headers don't. Requires prefix-stable templates.

DPO

dpo_tune_cache.py · preference_tulu_tokenize… 
{ "chosen":   [ …full conversation… ],
  "rejected": [ …same prompt, worse reply… ] }
→ chosen_/rejected_ input_ids · labels

Reuses the SFT tokenizer on each side (last_turn_only=True). Reference-model logprobs are computed once, up front, and cached — so DPO training holds a single model in memory.

RLVR

grpo_fast.py · rlvr_tokenize_v1 (→ v3) 
{ "messages": [ …prompt… ],
  "ground_truth": "72"  |  [tests…]  |  {constraints},
  "dataset": "gsm8k" }
→ input_ids_prompt · ground_truth · dataset

No labels at all — the model generates its own. ground_truth is polymorphic, and dataset is not provenance: it's the verifier-routing key (provenance lives in dataset_source).

The classic footgun

Mix weights are parsed by decimal point: "1.0" means 100% of the dataset, "3.0" means 3× upsampled — but "1" means exactly one sample. --dataset_mixer_eval_list gsm8k 16 = 16 eval examples. The docstring warns you; production YAMLs use both conventions deliberately (Olmo 3's instruct DPO mixes by absolute counts: 125000).

Masking is where SFT bugs live

The masker (_tokenize_tulu_sft_with_assistant_labels) renders each prefix of the conversation twice — once with the assistant header, once through the end of the turn — and unmasks tokens whose character offsets overlap the content span (overlap, not containment, so a boundary token like a leading-space-merged " ok" still trains). One production consequence documented in docs/olmo3.md: Think SFT data is deliberately tokenized with the Instruct chat template, because the Think template puts <think> inside the generation prompt where it would be masked — and the model would never learn to emit it. Every trainer prints a color-coded token visualization (visualize_token_role) on startup precisely so humans can catch this class of bug.

Decontamination is a search problem

The decontamination/ tool indexes every training set in Elasticsearch (user turns only) and sweeps the whole eval suite against it three ways: exact phrase, n-gram coverage (score = fraction of eval tokens covered by one training doc), and embedding kNN (NV-Embed-v2). Tülu 3's rule: a training set is contaminated if >2% of any eval overlaps at >50% token coverage. This is why dataset names carry scars — evol_codealpaca_heval_decontaminated (the original overlapped 70.7% of HumanEval), and why ShareGPT and LMSYS-Chat-1M were rejected outright (90.3% overlap with a safety eval).

Environments & rewards

RLVR: the reward model is a function

The heart of RLVR is a one-file abstraction, ground_truth_utils.py: a VerifierFunction takes (prediction, ground_truth, query) and returns a score in [0,1] (plus a dollar cost, because some verifiers are LLM judges). A registry is built by reflection over VerifierFunction.__subclasses__(), keyed by name — and each RL prompt's dataset column selects its verifier. One prompt can carry several (ground_truth, verifier) pairs; their weighted scores sum. The final reward is 10 × score by default, with an optional R1-style format gate (off in production — it destabilized response length) and a −10 overwrite for rollouts that never emitted EOS.

Code rewards are a microservice

The CodeVerifier doesn't run code — it POSTs {program, tests} to a FastAPI service (code_utils/api.py) that executes each test in its own OS process with a hard join-timeout and kill. In-process guards (an import denylist plus OpenAI's reliability_guard) are explicitly labeled "NOT a security sandbox" — real isolation is the container, and the production Olmo 3 runs pointed this at AWS Lambda. Scoring is a pass-rate with a cliff: below code_pass_rate_reward_threshold (0.99 in production, i.e. effectively all-tests-pass) the reward is zero.

Environments: three ways to be stateful

The environments/ package generalizes single-turn RLVR to tool use and multi-turn tasks. Three subclassing strategies: a stateless Tool (Python execution, Serper web search, Jina browsing, any MCP server — auto-discovered schemas included); a stateful RLEnvironment the model drives via function calls (a Docker sandbox exposing execute_bash); and a TextRLEnvironment where the model's entire generation is the action (Wordle is the reference implementation). Each concurrent rollout gets its own environment instance from a Ray actor pool, per-turn env rewards are folded into the final verifier score (last-turn or sum aggregation), and — crucially — tool-output tokens are masked out of the loss (mask_tool_use=True): the model shouldn't be trained to imitate the observation it received.

Frontier-relevant detail

Rewards can be rubrics that evolve during training: a RubricManager watches good-vs-bad rollouts for each prompt and asks a judge model to invent new discriminative criteria mid-run, which then override that prompt's ground truth. Reward engineering as an online process, not a fixed dataset property.

The RL training loop

OlmoRL: an inference system with a learner attached

The single most important systems fact: at 32K-token responses, generation dominates. Olmo 3's 7B Think RL runs 16 learner GPUs against 16–56 vLLM GPUs, the 32B run 96 against 48 — and the learner still idles ~75% waiting for data. So grpo_fast.py is architected as a fully asynchronous actor/learner system: disjoint GPU pools connected by Ray queues, rewards computed inside the inference actors, and weights broadcast over NCCL from a dedicated thread — updating vLLM engines mid-generation without dropping the KV cache ("inflight updates"). A rollout can be half-written by step-k weights and half by step-k+1.

Live sketch of one training step. Prompts (grey) queue into vLLM actors; each prompt fans out into a group of 8 samples, scored by verifiers inside the actor (pink = rewarded result). The data-prep actor filters zero-variance groups, computes centered advantages, packs sequences, and feeds learners. Weight sync (dashed) interrupts nothing.

The recipe

Why SFT → DPO → RLVR, in numbers

Each stage has a distinct job. SFT (~2.3M prompts for Think, from the Dolci suite: OpenThoughts3 math, QwQ-verified instruction-following, R1-trace chat) installs formats and skills. DPO sharpens with contrast — Olmo 3's twist is delta learning: pairs of Qwen3-32B (chosen) vs Qwen3-0.6B (rejected) outputs. Continued SFT on the same chosen data made the model worse (70.3→64.5 avg); DPO on the pairs made it better (72.9). The gap between responses teaches what absolute quality can't. RLVR then optimizes directly against verifiers — and starting it from DPO rather than SFT is worth +2.2 avg after RL.

RL-Zero: the control experiment the field needed

Every "RL on base models" paper before this ran on Qwen or Llama bases with unknown pretraining data — so nobody could rule out that "RL gains" were contamination sharpening. Olmo 3 RL-Zero runs RLVR directly on the fully documented base across four domains (math, code, precise IF, general chat), decontaminated against pretraining and midtraining. Both pass@1 and pass@32 rise on AIME — genuine frontier expansion, not distribution sharpening — and the spurious-reward negative control (random rewards) produces no gain, which is exactly what you want your benchmark to show.
