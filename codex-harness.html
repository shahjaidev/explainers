Inside the Codex harness.

Everything interesting about a coding agent lives outside the model. This is a component-by-component reading of OpenAI's open-source Codex CLI at commit 2b5bdcf — 99 Rust crates and ~1.27M lines that turn a token stream into edited files, guarded by three layers of permission machinery that all have to agree before a single command runs.

1 · the map

Seven layers, one narrow waist

The repo looks sprawling — codex-rs/ has 99 crate directories — but it has a strict shape. Every frontend (terminal UI, headless exec, IDE, desktop app, MCP server) speaks the same duplex protocol to codex-core. Core owns the turn loop and never touches a terminal; #![deny(clippy::print_stdout)] at the top of core/src/lib.rs enforces that literally. Below core, tools are dispatched through a single orchestrator that owns approvals and sandbox selection, and every process ultimately launches through one SandboxManager.

Click any box to see what it does and where it lives.

The Codex stack

Frontends → protocol → core → tool layer → execution → OS sandbox. Persistence and extension surfaces hang off the side.

frontend core / protocol tools execution & sandbox model I/O persistence extensions
The narrow waist. A frontend never calls a tool, never sees a sandbox, and never talks to the model API. It submits an Op and consumes Events. That's why the same core drives a ratatui TUI, a JSON-RPC app-server for IDEs, a headless CI runner, and Codex-as-an-MCP-server without any of them sharing code.

2 · the wire between UI and agent

Op in, Event out

The core exposes exactly two channels: a submission queue that accepts Submission { id, op } and an event queue that emits Event { id, msg }, correlated by submission id. Op has roughly 30 variants; EventMsg has well over a hundred. That asymmetry is the whole design — the UI asks for very few things, and the agent narrates everything it does.

Notice which Ops exist. Beyond UserInput and Interrupt, there is a whole family of answers: ExecApproval, PatchApproval, ResolveElicitation, UserInputAnswer, RequestPermissionsResponse. The agent asks questions mid-turn and blocks on a reply that arrives through the same queue as the original prompt. That single fact shapes the entire concurrency story downstream.

Duplex protocol

One submission queue, one event queue, correlated by id. Approvals travel back in on the submission queue while the turn is still running.

3 · objects and their lifetimes

ThreadManager → CodexThread → Session → Task

Four nested lifetimes, and confusing them is the fastest way to misread the code. ThreadManager is process-wide and owns the thread store, models manager, and auth. A CodexThread is one conversation — it holds the submission/event channels and the config snapshot. Inside it, a Session owns mutable state: history, active turn, MCP connections, input queue, unified-exec processes. And a task is one unit of work driven by a single Op.

The legacy names are still exported as deprecated aliases — ConversationManager, NewConversation, CodexConversation — which tells you the "thread" rename is recent and the whole app-server v2 protocol was built around it.

Ownership and lifetime nesting

Each box outlives everything drawn inside it. Only one task is active per session at a time; ActiveTurn is the mutex on that.

The submission loop

submission_loop (core/src/session/handlers.rs:714) is a plain while let Some(sub) = rx.recv() that dispatches on op. Turn-starting ops spawn a task and return immediately; answer-ops resolve a pending oneshot inside a still-running task. When the channel closes, the loop runs full thread teardown — aborting the active turn before emitting the thread-stop lifecycle, which the tests pin explicitly.

Four task kinds share one slot:

RegularTask

core/src/tasks/regular.rs

The normal agent turn. Wraps run_turn.

CompactTask

core/src/tasks/compact.rs

User-invoked /compact. Same summarization machinery as auto-compaction but with DoNotInject semantics.

ReviewTask

core/src/tasks/review.rs

Code review mode: spawns a child review thread with its own rubric prompt and exits back with a structured verdict.

UserShellCommandTask

core/src/tasks/user_shell.rs

A command the user typed (e.g. !ls), recorded into history so the model sees what happened.

4 · the heart

The turn loop, step by step

run_turn in core/src/session/turn.rs is the single most important function in the repo. Its doc comment states the contract plainly: the model replies with either function calls or an assistant message; function calls get executed and fed back; a bare assistant message ends the turn. Everything else in the 2,700-line file is the machinery that makes that true under compaction, steering, hooks, retries, and cancellation.

Walk through it. Steps 1–8 run once per turn; 9–17 are the loop body that repeats per sampling request.

What the sampling request actually does

Step 12 hides the most interesting concurrency in the codebase. try_run_sampling_request consumes the ResponseEvent stream and maintains a FuturesOrdered of in-flight tool calls. When an OutputItemDone carries a function call, its future is pushed onto that queue while the stream keeps arriving. Tool calls therefore start executing before the model has finished emitting its next item, and outputs are still returned to the model in the order they were requested.

There is a second subtlety: a commentary-phase assistant message or a reasoning item sets preempt_for_mailbox_mail. If a sibling agent has mail waiting, the harness breaks out of the stream early with needs_follow_up: true rather than letting the model keep talking — inter-agent messages get priority at natural boundaries.

Stream consumption and tool fan-out

One SSE/WebSocket stream in; N tool futures out; outputs re-ordered back into the prompt.

Termination is negotiated, not assumed. needs_follow_up = model_needs_follow_up || has_pending_input. Even when the model is done, a message the user typed while it was thinking keeps the loop alive. And even with nothing pending, a Stop hook can force continuation by returning a prompt — the harness records it as a hook message, sets stop_hook_active, and goes around again. Only a hook that declines to block actually ends the turn.

5 · the request view

StepContext: freezing the world for one sampling request

A subtle bug class in agent harnesses: the tool list you advertised to the model drifts from the tool list you'll dispatch against, because an MCP server reconnected or a plugin loaded in between. Codex solves it with a value type captured once per sampling request.

Note #[deprecated] cwd — the codebase is mid-migration from "the session has a working directory" to "each turn environment has its own," which is what makes remote and multi-root execution possible.

Building the tool plan

tools/spec_plan.rs is where the model's tool menu gets assembled, and it is almost entirely conditional. Shell tools depend on the model's ConfigShellToolType; when unified exec is active the legacy shell tool is still registered but with ToolExposure::Hidden so code-mode can call it without the model seeing it. MCP resource tools appear only if any server is configured. Collaboration tools appear only in multi-agent mode. A guardian reviewer session gets a hard-coded three-tool allowlist — exec_command, write_stdin, view_image — and nothing else, no matter what the config says.

Filter the registry:

Exposure is a first-class concept. ToolExposure distinguishes Direct (model sees and calls it), DirectModelOnly (visible to the model but excluded from code-mode's TypeScript surface), and Hidden (dispatchable but never advertised). Plus a deferred-namespace mechanism: tools can be collapsed behind a search tool and their schemas fetched on demand, which is how the harness keeps the advertised tool list small when dozens of MCP servers are connected.

6 · from token to process

The tool dispatch pipeline

A function call named by the model travels through eight distinct stages before anything executes, and through three more on the way back. Two of those stages can rewrite the call, three can veto it, and one can restart it under different privileges. Click through the pipeline:

The orchestrator's retry ladder

The module header for tools/orchestrator.rs describes the whole design in four lines: "approval → select sandbox → attempt → retry with an escalated sandbox strategy on denial (no re-approval thanks to caching)."

The retry is conditional on three separate gates. The error must actually be SandboxErr::Denied. The tool must opt in via escalate_on_failure(). And the policy must permit it via wants_no_sandbox_approval() — under Never or OnRequest there is no silent unsandboxed retry; the harness surfaces a concise denial that preserves the original output instead. That last branch is what stops a sandbox from degrading into a suggestion.

7 · who says yes

Three independent approval systems

Codex does not have "an approval prompt." It has a policy enum, a rules engine, a static safety analyzer, and an LLM reviewer — and a command has to survive all of the ones that apply.

1 · AskForApproval — the policy

protocol/src/protocol.rs:917

UnlessTrustedonly is_safe_command() read-only commands auto-approve; everything else prompts
OnRequest defaultthe model decides when to ask
Granular{…}five independent booleans — see below
Nevernever prompt; failures go straight back to the model

Granular splits approval by source: sandbox_approval (shell escalation), rules (execpolicy prompt rules), skill_approval, request_permissions (the tool), mcp_elicitations. A false field does not mean "ask" — it means auto-reject. That's the difference between a policy and a preference.

2 · execpolicy — the rules engine

core/src/exec_policy.rs · execpolicy/

A Starlark-ish rule language loaded from layered .rules files, evaluated per command to a Decision. Rules can allow a prefix, deny it, or force a prompt. Amendments are appended at runtime when a user approves "always allow cargo test" — blocking_append_allow_prefix_rule writes it back to the rules file.

It also carries a BANNED_PREFIX_SUGGESTIONS list — bash -lc, sh -c, python -c, bun -e, Rscript and friends. You cannot "always allow" an interpreter, because allowing the interpreter allows everything.

3 · safety.rs — static analysis

core/src/safety.rs

assess_patch_safety returns AutoApprove / AskUser / Reject. Even when a patch is provably confined to writable roots it still runs sandboxed — the comment explains why: paths in the patch may be hard links to files outside the writable roots. And auto-approval requires that a sandbox actually be available on this platform; where get_platform_sandbox() returns None, it falls back to asking rather than trusting the path analysis.

4 · the Guardian — an LLM reviewer

core/src/guardian/

When ApprovalsReviewer routes to the guardian, an on-request approval is answered by a separate model session instead of the user. It gets a compacted transcript (10k tokens of messages, 10k of tool output, 40 recent entries), the exact planned action, and must return strict JSON.

Fails closed on timeout (90s), execution failure, or malformed output. Circuit breaker at 3 consecutive denials per turn. The guardian inherits the parent's network proxy and allowlist, so it can't be used to widen access.

8 · the last line

Four sandbox backends behind one enum

SandboxType has exactly four values — None, MacosSeatbelt, LinuxSeccomp, WindowsRestrictedToken — and get_platform_sandbox() is a four-line function that picks one by cfg!(target_os). On Windows it returns None unless the Windows sandbox is explicitly enabled, which is why the Windows path has its own escalation level and its own read-grant system.

Everything above the enum is policy; everything below is a transform() that rewrites a command into a sandboxed command.

The network is a separate sandbox

Filesystem confinement and network confinement are orthogonal in this design. Network policy is enforced by codex-network-proxy, a full MITM proxy the harness runs itself: it generates a CA, injects it into the sandboxed process's trust store via with_managed_mitm_ca_readable_root, and terminates TLS so it can apply per-domain rules. It speaks both HTTP CONNECT and SOCKS5, has a credential broker so secrets can be injected into outbound requests without the agent ever seeing them, and does TCP attribution on Windows to tell which process opened a connection.

When a request is refused, the denial doesn't just fail — begin_network_approval can put the tool call into a deferred approval state, cancel the in-flight connection, ask the user, and let the command continue. That's why SandboxAttempt carries both a network_denial_cancellation_token and a network_proxy handle.

How a command actually gets launched

Denial detection is a heuristic, and they know it. is_likely_sandbox_denied exists because seatbelt, landlock, and Windows all report refusal differently, and sometimes only as an exit code plus a message on stderr. The shared helper keeps escalation behaviour consistent across every exec path rather than each tool guessing on its own.

9 · what "run a command" means

Five execution runtimes

unified exec — the PTY runtime

core/src/unified_exec/ · handlers exec_command + write_stdin

The modern shell tool. Commands run in a real PTY, processes persist across tool calls, and the model interacts with them via write_stdin. That single change turns "run a command" into "drive an interactive session" — you can start a REPL, a debugger, or a dev server and keep talking to it.

Bounded hard: 64 concurrent processes, 1 MiB output buffer per process (head/tail retention), yield windows from 250 ms to 30 s, background terminals capped at 300 s by default. Windows gets a 10 s initial yield floor because process startup is slower there.

shell command — the legacy runtime

core/src/tools/runtimes/shell.rs

One command, captured output, exit. Still registered (often hidden) because it is simpler to reason about, works where PTYs don't, and is what older model checkpoints were trained against. unix_escalation.rs — 1,089 lines — handles the "run this one thing with more privilege" path.

apply_patch — structured edits

apply-patch/ · handlers/apply_patch.rs + apply_patch.lark

A dedicated patch format with a Lark grammar, not a diff library. Parsed into ApplyPatchAction with typed ApplyPatchFileChange entries, safety-assessed as a unit, then applied. Because the change set is structured before it touches disk, assess_patch_safety can reason about every target path up front — which a shell sed could never allow.

code mode — tools as a TypeScript API

code-mode/ · code-mode-runtime/ (V8)

Instead of emitting one function call per action, the model writes a program that calls tools, executed in an embedded V8 runtime. Each tool's JSON Schema is rendered to a TypeScript declaration (render_json_schema_to_typescript) and grouped into namespaces; the model gets two tools, exec and wait. Nested tool calls made from inside the script re-enter the same registry — same approvals, same sandbox.

exec-server — local and remote environments

exec-server/ (37 modules)

The abstraction that lets a turn execute somewhere other than this machine. It defines an environment with a filesystem and a process API, implemented locally (local_process, local_file_system) or remotely over a Noise-encrypted channel with a rendezvous relay. Capability roots are discovered and cached per environment; a turn can bind several, which is why tool schemas grow an environment_id parameter when more than one is selected.

MCP tool calls

core/src/mcp_tool_call.rs (2,229 lines)

External MCP servers get their tools merged into the same registry, with their own approval templates, elicitation flow (a server can ask the user a structured question mid-call), resource tools (list/read), and a tool-exposure filter so a server can't silently flood the model's tool list.

10 · the finite resource

Context management and compaction

Conversation history is not a Vec<Message> you append to. ContextManager owns it, for_prompt(&input_modalities) renders a model-appropriate view of it, and a separate world state tracks the environment facts injected alongside it. Every turn diffs the world state against a baseline and injects only what changed.

What gets injected, and when

The core/src/context/ directory is a catalogue of everything the harness can silently add to your conversation — 35+ fragment types. It's the most honest inventory of "what the agent knows that you didn't tell it" I've seen in an open codebase:

Three compaction implementations

When history approaches the limit, the harness summarizes and replaces. There are three paths — local inline, remote, and remote v2 — chosen by should_use_remote_compact_task(provider). But the load-bearing detail is where the summary goes, and the comment in compact.rs is unusually explicit about why:

"Mid-turn compaction must use BeforeLastUserMessage because the model is trained to see the compaction summary as the last item in history after mid-turn compaction; we therefore inject initial context into the replacement history just above the last real user message."

That is a harness invariant dictated by post-training. Put the summary in the wrong slot and the model behaves differently — the layout of compacted history is part of the model's interface, not an implementation detail.

Compaction trigger points in a turn

Compaction is instrumented like a production system. Every run emits a CodexCompactionEvent carrying implementation, strategy, phase (PreTurn/MidTurn), reason (ContextLimit/manual), trigger, and terminal status. There are PreCompact and PostCompact hooks. And compact_model_fallback.rs exists for when the summarizing model itself is unavailable — the failure mode of "can't compact, can't continue" was clearly hit in practice.

11 · remembering

Rollouts, the state DB, and the thread store

Three storage systems with three different jobs, and it's worth being precise about which is which.

rollout — append-only JSONL

rollout/src/recorder.rs

One .jsonl per session, written by a dedicated task behind an mpsc channel so the turn loop never blocks on disk. Lines are RolloutLines wrapping SessionMeta, TurnContext, WorldState, Compacted, ResponseItem, EventMsg, or inter-agent traffic. Has a reverse JSONL scanner so "resume the last session" doesn't read the whole file.

state DB — SQLite

state/ + rollout/src/state_db.rs

Versioned migrations, a log DB, an audit trail, telemetry. Backs listing, search, and indexing across sessions — the things a flat JSONL is bad at. The CLI ships a state_db_recovery module, which tells you it has been corrupted in the field.

thread store

thread-store/

The typed API over both: StoredThread, StoredThreadHistory, ThreadMetadataPatch, plus a live_thread view and section-based reads so a client can page history without loading it all.

What is deliberately not persisted

rollout/src/policy.rs is a small file that carries a lot of judgment. should_persist_response_item returns false for AdditionalTools, CompactionTrigger, and Other — transient control items that would confuse a replay. And persistence is filtered by ThreadHistoryMode, so an ephemeral thread can run the whole machinery while writing nothing durable.

The payoff is fork: ForkSnapshot plus rollout reconstruction lets you branch a conversation from an arbitrary point. There are 1,959 lines of tests for reconstruction alone (session/rollout_reconstruction_tests.rs) — replaying a log into an identical live session is evidently hard to get right.

Config is layered, not merged

Nine config layer sources with explicit integer precedence (config/src/config_layer_source.rs). Read the ordering as a statement about trust:

MDM sits at the bottom because it is overridden by more specific layers — but separately, ConfigRequirements lets a managed layer publish constraints that clamp what higher layers may set. That's why TurnContext.approval_policy is a Constrained<AskForApproval> rather than a plain enum: an enterprise can pin the ceiling even though session flags win on precedence.

12 · the pluggable edges

Five ways to change what the agent does

PreToolUse, PostToolUse, UserPromptSubmit, SessionStart, Stop, SubagentStop, PermissionRequest, PreCompact, PostCompact, Notification. Hooks are configured with matchers per event and run through hooks/src/engine with output spilling to disk when it's large.

They are not observers. PreToolUse can return Blocked(reason) or rewrite tool_input — and the tool runtime must be able to reconstruct itself from the rewritten value, which is what with_updated_hook_input and the "stable hook contract" comments in registry.rs are about. Stop can refuse to let the turn end and supply a continuation prompt. PermissionRequest can answer an approval without a human.

Inbound: external MCP servers contribute tools and resources, with prewarming (mcp_prewarm.rs), incremental startup events, per-server refresh, dependency installation prompts for skills, and an exposure filter. required_mcp_servers_for_input means a server can be started lazily because the user's message mentioned it.

Outbound: codex mcp-server exposes Codex itself as an MCP server over stdio, so another agent can call it as a tool. The core is symmetric about this.

Loaded from layered roots (bundled, user, project, plugin), matched against the user's message by explicit @mention or implicit detection, and injected as prompt fragments. detect_implicit_skill_invocation_for_command goes further: it watches the commands the agent runs and fires a skill-invocation analytics event when a command matches a skill's signature, i.e. it notices when the model reinvented a skill by hand.

Skills can declare MCP dependencies; maybe_prompt_and_install_mcp_dependencies offers to install them mid-turn.

core-plugins/ is the largest extension crate: manifests, loaders, npm sources, bundle archives, marketplace add/remove/upgrade, marketplace policy (an enterprise can restrict allowed source kinds), and command migration from older formats. A plugin can ship skills, MCP servers, hooks, and slash commands as one unit.

There's also a discovery loop: prepare_tool_recommendations asks a backend endpoint which plugins would help with the current turn, then exposes list_available_plugins_to_install and request_plugin_install as tools — the model can ask to install its own capabilities, subject to approval.

Under the collaboration namespace: spawn_agent, send_message, followup_task. A spawned agent is a real thread with its own session, inheriting config and optionally forking the parent's history (spawn_forked_thread). Communication flows back as Op::InterAgentCommunication and lands in history as messages.

Two protocol versions coexist (multi_agents.rs and multi_agents_v2.rs) with 4,538 lines of tests between them. The mailbox-preemption logic in the streaming loop exists specifically so a parent notices a child's message at a reasoning boundary instead of after it has finished a long monologue.

One detail worth stealing. ToolCall::direct_source() checks whether a collaboration tool call arrived with empty encrypted_function_args and, if so, tags it DirectPlaintextMessage — after which tool_log_payload logs the literal string "[plaintext arguments]" instead of the content. Inter-agent messages are treated as potentially sensitive user data at the logging layer, not just the storage layer.

13 · what the code argues

Eight things this harness believes

The StepContext pattern. MCP servers reconnect, plugins load, environments come and go — all asynchronously. Capturing tool router, MCP binding, environments, and AGENTS.md into one immutable value per sampling request eliminates an entire family of races, at the cost of one Arc clone.
Every tool that touches the outside world goes through ToolOrchestrator::run. Not a shared helper you're encouraged to call — the actual path. That's what makes "no re-approval on escalated retry" and "guardian review substitutes for the user" implementable as single edits rather than a policy sprinkled across a dozen handlers.
The guardian denies on timeout, on malformed JSON, on execution failure. It also breaks the circuit after 3 consecutive denials per turn and keeps a 50-entry denial window, because an agent stuck in a rejection loop is its own failure mode. Both halves matter: the safe default, and the escape from the safe default.
In assess_patch_safety, a patch confined to writable paths is only auto-approved if a platform sandbox exists. No sandbox available means ask the user, because the path analysis can be defeated by hard links. Refusing to auto-approve on the basis of unenforceable reasoning is the rare correct call.
BANNED_PREFIX_SUGGESTIONS blocks bash -lc, sh -c, python -c, bun -e, Rscript and friends from becoming saved allow-prefixes. Allow-listing by command prefix is only meaningful if the prefix constrains behaviour, and an interpreter constrains nothing.
A turn ends when the model has nothing more to say and no steering input is queued and no Stop hook wants to continue. Treating "assistant message with no tool call" as the sole end condition is the naive version, and this codebase has three separate overrides on top of it.
Mid-turn compaction must place the summary last, because that's what the model was trained on. Harness and post-training are coupled through the exact shape of the context window — a fact that's invisible from the outside and load-bearing on the inside.
Unified exec's persistent PTYs turn the shell from a request/response tool into a session the agent can hold open. That one change is why the harness needs a process manager, output ring buffers, yield-time tuning, background-terminal cleanup as an explicit Op, and a cap of 64 — and it's the difference between an agent that runs commands and one that uses a computer.
Read it yourself. Start at codex-rs/core/src/session/turn.rs and follow run_turn → run_sampling_request → try_run_sampling_request. Then read tools/orchestrator.rs top to bottom — it's 528 lines and it is the security model. Everything else is detail hanging off those two files.
