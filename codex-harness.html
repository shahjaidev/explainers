1 · the motivating constraints

Seven problems the harness exists to solve

It's tempting to read an agent codebase as an accumulation of features. It isn't. Nearly every non-obvious structure in Codex traces back to a small set of hard constraints, and once you know which constraint a piece of code is answering, the code stops looking arbitrary.

Here are the seven, each with the mechanism it produced. Click through them — the rest of this page is a long-form version of this list.

3 · why a protocol at all

The narrow waist, and the reason it has to be duplex

Codex ships as a terminal UI, a headless CI runner, an IDE backend, a desktop app, and an MCP server. Sharing a core across five frontends is easy; the hard part is that the agent needs to ask questions mid-turn — approve this command, answer this MCP elicitation, pick one of these options — and a request/response API can't express that.

So the waist is two queues, not a function call. Submission { id, op } in, Event { id, msg } out, correlated by id. Roughly 30 Ops versus well over a hundred EventMsg variants: the UI asks for very little, the agent narrates everything. And crucially, answers come back in on the same submission queue while the turn is still running — ExecApproval, PatchApproval, ResolveElicitation, UserInputAnswer, RequestPermissionsResponse.

Duplex protocol

Approvals travel back in on the submission queue while the turn is still running. That single requirement is why this is a protocol and not an API.

Design consequence. Because approvals are ordinary submissions, Op::ThreadSettings also goes through the queue rather than mutating config directly — the comment says why: "this uses the same submission queue as turn starts so app-server can preserve caller order between both kinds of mutation." Once you have a queue, everything that must be ordered relative to a turn has to enter through it.

4 · the heart

The turn loop, step by step

run_turn in core/src/session/turn.rs states its contract plainly: the model replies with either function calls or an assistant message; function calls get executed and fed back; a bare assistant message ends the turn. The other 2,700 lines are what it takes to keep that true under compaction, steering, hooks, retries, and cancellation.

Steps 1–8 run once per turn; 9–17 repeat per sampling request.

Why tool calls start before the stream ends

Step 12 contains the most interesting concurrency in the repo. try_run_sampling_request consumes the ResponseEvent stream and maintains a FuturesOrdered of in-flight tool calls. When an OutputItemDone carries a function call, its future is pushed while the stream is still arriving. Latency motivation: a model that emits three tool calls shouldn't pay for them serially after it finishes talking. Ordering motivation: FuturesOrdered returns results in request order, so the prompt the model sees next is deterministic regardless of which tool finished first.

A second subtlety: a commentary-phase assistant message or a reasoning item sets preempt_for_mailbox_mail. If a sibling agent has mail waiting, the harness breaks out early with needs_follow_up: true rather than letting the model keep going — inter-agent messages get priority at natural boundaries, not arbitrary ones.

Stream consumption and tool fan-out

Termination is negotiated, not assumed. needs_follow_up = model_needs_follow_up || has_pending_input. A message typed while the model was thinking keeps the loop alive. And even with nothing pending, a Stop hook can force continuation by returning a prompt. Treating "assistant message with no tool call" as the end condition is the naive version; this codebase has three overrides on top of it.

5 · a race you only find in production

StepContext: freezing the world for one request

The motivating bug: you advertise a tool list to the model, and by the time the model calls one of those tools an MCP server has reconnected, a plugin has loaded, or an environment has dropped. Now you're dispatching against a different tool set than the one you described. In a long-running agent with lazily-started servers this is not a rare race — it's the normal case.

The fix is a value type captured once per sampling request, holding the exact MCP binding, the finalized tool router, the environment snapshot, capability roots, and the AGENTS.md that was observed with them. A tool future spawned during step k holds its Arc<StepContext> alive even after the turn moves on.

6 · what the model is handed

The tool set is computed, not declared

There is no static list of Codex's tools. tools/spec_plan.rs — 1,153 lines — computes the registry on every sampling request from the model's declared capabilities, the enabled feature flags, the connected MCP servers, the selected environments, the loaded plugins, the collaboration mode, and the session source.

The motivation is that a tool the model can't use correctly is worse than no tool. A model checkpoint trained on the one-shot shell tool shouldn't be handed exec_command+write_stdin; a session with no environment shouldn't advertise a shell at all; a guardian reviewer must not be able to write files. So gating is per-tool and evaluated fresh.

Parallelism is a per-tool property

ToolCallRuntime holds a single Arc<RwLock<()>> named parallel_execution, and the trick is which guard each tool takes:

let _guard = if supports_parallel {
    Either::Left(lock.read().await)    // many concurrent
} else {
    Either::Right(lock.write().await)  // exclusive
};

A parallel-safe tool takes a read guard, so any number can run together. A tool that can't tolerate concurrency — anything mutating the working tree, for instance — takes the write guard and drains everything else first. One lock, no scheduler, no per-tool queues, and the property is declared on the runtime rather than enforced by convention.

Separately, wait_until_ready() lets a runtime block on its own prerequisite (an MCP server still starting, an environment still handshaking) before taking the gate — so a slow tool doesn't hold the exclusive lock while it waits for something unrelated.

7 · the problem nobody has at 10 tools

Tool discovery: how the list stays small

Here is the constraint that shapes this entire subsystem. Every tool schema you advertise costs input tokens on every single sampling request of the conversation, and it competes for the model's attention with the tools it actually needs. Connect eight MCP servers with twenty tools each and the tool list alone can outweigh the conversation.

Codex attacks this from four directions at once.

The funnel: from everything registered to what the model is shown

Illustrative scenario — 6 MCP servers, plugins loaded, code mode off. Toggle the mechanisms to see what each one removes.

1 · Deferred exposure — MCP tools are never in the initial list

The single highest-leverage line in the discovery system is in mcp_tool_exposure.rs:

let exposure = if search_tool_enabled {
    ToolExposure::Deferred
} else {
    ToolExposure::Direct
};

When the model supports the search tool, every MCP tool is registered as Deferred — fully dispatchable, completely absent from the advertised list. The model doesn't know they exist until it goes looking. When the model doesn't support search, the same tools fall back to Direct and the old behaviour returns. One flag, two regimes, no separate code path.

Gate: search_tool_enabled = model_info.supports_search_tool && provider.capabilities().namespace_tools. And finalize_tool_router only registers the search tool at all if at least one other tool is deferred and has search metadata — no empty search tool cluttering the list.

2 · tool_search — BM25, locally, over tool descriptions

The retrieval is not a model call and not an embedding lookup. It's BM25 from the bm25 crate, built over one document per deferred tool, where the document text is derived from the tool's name, description, and parameter schema. Default limit: 8 results.

Why BM25 and not embeddings

No network call, no model, no cache to invalidate, no API key, and it runs in microseconds inside the tool call the model already made. Tool names and descriptions are short, keyword-dense, and written by developers — exactly the regime where lexical retrieval is competitive. The engine is rebuilt only when the tool set changes, guarded by ToolSearchHandlerCache keyed on the search infos themselves.

What comes back

Not text — specs. ToolSearchInfo::from_spec pre-builds each deferred tool's spec with defer_loading = true and output_schema stripped, so a search result is a real, immediately-callable tool definition. coalesce_loadable_tool_specs merges hits that belong to the same namespace so the model gets one coherent group rather than three fragments of it.

3 · Mentions — the user shortcuts the search

Search is the model's path. The user has a faster one: two sigils, defined in utils/plugins/src/mention_syntax.rs as $ for tools and @ for plugins, plus mcp://server path mentions.

What makes this more than autocomplete is when it is resolved. required_mcp_servers_for_input runs at step 2 of the turn — before the step context is captured, before the tool plan is built. A mentioned plugin contributes its mcp_server_names to a required set; those servers are started; only then is the registry assembled. The mention doesn't just select a tool, it causes the server behind it to exist.

That ordering is why lazy MCP startup is viable at all: servers stay cold until something references them, and referencing them is cheap because the reference is resolved before the tool list is computed.

4 · Suggestion — tools the user doesn't have yet

The last direction is outward. prepare_tool_recommendations asks a backend endpoint which plugins or connectors would help with this turn, and the answer takes one of two presentations:

  • RecommendationContext — the backend returned candidates, and they're injected as context so the model simply knows they're installable.
  • ListTool — fall back to locally discoverable connectors and plugins, and register list_available_plugins_to_install so the model can enumerate them.

Either way, request_plugin_install is registered and the model can ask to extend its own capability set — routed through approval like any other consequential action, and filtered per client via filter_request_plugin_install_discoverable_tools_for_client because a headless CI runner shouldn't be offering interactive installs.

Apps get a policy evaluator, not just a filter. Connector tools from the Codex Apps MCP server pass through AppToolPolicyEvaluator, which sees the tool's destructive_hint and open_world_hint annotations along with its connector id — so an administrator can disable, say, all destructive tools from a given connector without disabling the connector. Discovery and permissions are the same decision here.

Code mode inverts the whole thing

When code mode is on, the model isn't shown tools at all — it's shown exec and wait, and the tools are rendered into a TypeScript API via render_json_schema_to_typescript, grouped into namespaces. The tool list collapses to two entries; capability is expressed as a type surface the model writes against.

This is why ToolExposure needed the DirectModelOnly and Hidden distinctions in the first place. Some tools belong in the script surface, some only in the direct surface, some in neither — and spec_plan has explicit is_excluded_from_code_mode and is_hidden_by_code_mode_only checks plus a configurable direct_only_tool_namespaces list to place them.

9 · who says yes

Four approval systems, because one is never enough

Codex doesn't have "an approval prompt." It has a policy enum, a rules engine, a static safety analyzer, and an LLM reviewer — motivated by four different threat models. The policy handles user intent. The rules engine handles site-specific bans. The analyzer handles what can be proven about a patch before it runs. The guardian handles the case where a human isn't there to ask.

2 · execpolicy

core/src/exec_policy.rs

Layered .rules files evaluated per command to a Decision: allow a prefix, deny it, or force a prompt. Runtime amendments append when a user says "always allow cargo test".

And a BANNED_PREFIX_SUGGESTIONS list — bash -lc, sh -c, python -c, bun -e, Rscript — that can never become saved allow-prefixes. Prefix allow-listing only means something if the prefix constrains behaviour; an interpreter constrains nothing.

3 · safety.rs

core/src/safety.rs

assess_patch_safety → AutoApprove / AskUser / Reject. A patch provably confined to writable roots is still run sandboxed, because a path in it may be a hard link to somewhere else. And auto-approval requires that a sandbox actually exist on this platform — where it doesn't, the analyzer asks rather than trusting its own reasoning.

4 · the Guardian

core/src/guardian/

A separate model session answers approvals when no human will. It gets a compacted transcript (10k tokens of messages, 10k of tool output, 40 recent entries) plus the exact planned action, and must return strict JSON. Fails closed on timeout (90 s), execution failure, or malformed output; circuit-breaks after 3 consecutive denials per turn; inherits the parent's network proxy so it can't be used to widen access.

10 · the last line

Four backends behind one enum

SandboxType has four values — None, MacosSeatbelt, LinuxSeccomp, WindowsRestrictedToken — and get_platform_sandbox() is a four-line function. Everything above the enum is policy; everything below is a transform() that rewrites a command into a sandboxed command. The motivation for that split is that policy has to be testable without a kernel, and 992 lines of policy_transforms_tests.rs plus 1,455 lines of seatbelt_tests.rs are the payoff.

Escalation, and why it is conditional

The orchestrator's module header states the design in one line: "approval → select sandbox → attempt → retry with an escalated sandbox strategy on denial (no re-approval thanks to caching)." The interesting part is the three gates on that retry. The error must be a real SandboxErr::Denied. The tool must opt in via escalate_on_failure(). And the policy must permit it via wants_no_sandbox_approval() — under Never or OnRequest there is no silent unsandboxed retry, only a concise denial that preserves the original output.

Without that third gate the sandbox degrades into a suggestion: everything gets denied once and then runs anyway.

Escalation on sandbox denial

The network is a separate sandbox. Filesystem and network confinement are orthogonal here. codex-network-proxy is a full MITM proxy the harness runs itself: generates a CA, injects it into the sandboxed process's trust store, terminates TLS to apply per-domain rules, speaks HTTP CONNECT and SOCKS5, and includes a credential broker so secrets are injected into outbound requests the agent never sees. A refusal can become a deferred approval — cancel the connection, ask the user, resume — which is why SandboxAttempt carries both a cancellation token and a proxy handle.

11 · what "run a command" means

Six execution runtimes

unified exec — persistent PTYs

core/src/unified_exec/

Commands run in a real PTY and outlive the tool call; the model drives them with write_stdin. That converts "run a command" into "hold a session open" — REPLs, debuggers, dev servers. Bounded hard: 64 processes, 1 MiB head/tail buffers, 250 ms–30 s yield windows, 300 s default background cap, 10 s initial yield floor on Windows.

shell command — one-shot

tools/runtimes/shell.rs

Simpler to reason about, works where PTYs don't, and matches what older checkpoints were trained on. Kept registered — often Hidden — rather than deleted.

apply_patch — structured edits

apply-patch/ + apply_patch.lark

A patch format with a Lark grammar, parsed into typed ApplyPatchFileChange entries before anything touches disk. That ordering is the point: the safety analyzer can reason about every target path up front, which a shell sed could never allow.

code mode — V8

code-mode-runtime/

The model writes a TypeScript program that calls tools as functions. Nested calls re-enter the same registry, same approvals, same sandbox — the script is a scheduling convenience, not an escape hatch.

exec-server — environments

exec-server/ (37 modules)

Filesystem + process APIs implemented locally or over a Noise-encrypted relay to a remote executor. Capability roots are discovered and cached per environment; a turn may bind several, which is why tool schemas grow an environment_id parameter when more than one is selected.

MCP tool calls

core/src/mcp_tool_call.rs

External servers merge into the same registry with their own approval templates, elicitation flow, resource tools, and exposure policy — 2,229 lines of it.

12 · the finite resource

Compaction: what survives, and why it lands where it does

Every long agent session eventually hits the context window, and the response is always some form of "summarise and continue." What makes Codex's implementation worth reading is that it has four of them, a non-obvious trigger calculation, an explicit and surprising retention policy, and one hard constraint imposed by how the model was trained.

When: the trigger is two limits, not one

context_window_token_status (core/src/session/context_window.rs) computes a status object every sampling request. Two independent ceilings can fire it:

token_limit_reached =
      auto_compact_scope_tokens >= (auto_compact_scope_limit + fallback_buffer)
   || active_context_tokens     >= full_context_window_limit

The second is the model's hard context window. The first is a soft auto-compact limit, and it has a scope setting that reveals the real motivation:

AutoCompactTokenLimitScope::Total

Count everything in the active context against the limit. Simple, and what you'd write first.

::BodyAfterPrefix

Subtract the window's prefill_input_tokens baseline and count only what accumulated after the initial prefix. The prefix — instructions, environment context, tool specs — is stable and prompt-cached; charging conversational growth against a budget that already includes it would trigger compaction far too early on a session with a big tool list. This scope makes the budget measure the thing that's actually growing.

There's also a deliberate slack term. fallback_buffer_tokens is added to the soft limit only when a fallback prompt exists to use it — reserving headroom for a graceful "you're nearly out, wrap up" message rather than a hard stop. And base_window_tokens_remaining is the minimum of the two remaining budgets, so whatever the UI shows is the honest number.

The local recipe

compact.rs:622 build_compacted_history

new_history =
    [ initial context (if mid-turn) ]
  + [ most recent user messages,
      newest-first until 20k tokens,
      the last one token-truncated ]

Assistant messages, reasoning items, every function call and every tool output: gone. collect_user_messages also skips any prior summary (is_summary_message), so summaries don't stack across compactions.

The remote recipe

compact_remote.rs:336 should_keep_compacted_history_item

Keeps: assistant messages, real user messages, persisted hook prompts, compaction items.
Drops: developer messages (the doc comment explains: "remote output can include stale/duplicated instruction content"), non-user-content user wrappers such as session prefixes, reasoning, and every tool item.

The filter runs on the model's own compaction output — the harness does not trust the server to have produced a clean transcript.

Two details in that recipe are worth pausing on. First, the summary is inserted as a user message, not an assistant message — so the next turn reads it as instruction rather than as something it said. Second, the prompt that generates it (prompts/templates/compact/prompt.md) is explicitly a handoff to a different model, not a recap:

You are performing a CONTEXT CHECKPOINT COMPACTION. Create a handoff summary for another LLM that will resume the task.

Include: current progress and key decisions made · important context, constraints, or user preferences · what remains to be done (clear next steps) · any critical data, examples, or references needed to continue.

And the receiving side is framed to match — SUMMARY_PREFIX begins "Another language model started to solve this problem and produced a summary of its thinking process…". The harness models compaction as a handover between two agents rather than as memory loss, which is a better fit for what actually happens to the model's behaviour.

Where: the placement constraint

The single most load-bearing comment in the compaction code:

"Mid-turn compaction must use BeforeLastUserMessage because the model is trained to see the compaction summary as the last item in history after mid-turn compaction; we therefore inject initial context into the replacement history just above the last real user message."

Pre-turn and manual compaction use DoNotInject — they clear the reference context item and let the next turn fully re-seed initial context. Mid-turn compaction can't do that, because the model expects to resume with the summary last. The layout of compacted history is part of the model's interface, coupled to post-training and invisible from outside.

Trigger points and injection modes

Failure modes they clearly hit

Compaction sends the whole history to the model, so it can fail with ContextWindowExceeded — the exact error it was invoked to prevent. The handler drops the oldest item and retries, with an explicit rationale: "trim from the beginning to preserve cache (prefix-based) and keep recent messages intact." The retry counter is reset to zero on each trim, because this isn't a transport failure. Only when a single item is left does it give up. 
Err(e) if matches!(e.details(), ContextWindowExceeded) => {
    if turn_input_len > 1 {
        history.remove_first_item();
        retries = 0;
        continue;
    }
    …
}
compact_model_fallback.rs exists for the case where compaction can't run on the intended model. should_retry_with_current_model and record_model_fallback let it fall back and record that it did — because "can't compact, therefore can't continue" is a dead session.
trim_function_call_history_to_fit_context_window estimates per-item tokens and replaces oversized tool outputs with "Output exceeded the available model context and was truncated". It deliberately accumulates in i128 so an overflow can't be hidden by i64 saturation in the normal estimator — a comment that only gets written after a real incident.
Every successful compaction emits a warning event: "Heads up: Long threads and multiple compactions can cause the model to be less accurate. Start a new thread when possible to keep threads small and targeted." The harness does not pretend compaction is free.
Every run emits a CodexCompactionEvent with trigger (auto/manual), reason (context limit / user requested), implementation, phase (PreTurn/MidTurn/StandaloneTurn), strategy, terminal status, error kind and HTTP status, active tokens before and after, retained image count, summary tokens, and cached/cache-write input tokens. Compaction is treated as a production system with its own SLOs, not a fallback path.

Telling the model how much room is left

The last piece is that compaction isn't purely reactive. With the token-budget feature on, the harness injects a reminder once the remaining window crosses reminder_threshold_tokens, using a message template and guidance text that the model itself ships — apply_model_defaults pulls reminder_threshold_tokens, reminder_message_template, guidance_message, auto_compact_fallback_prompt and auto_compact_fallback_buffer_tokens out of model_info.model_messages, and only if the user hasn't set them explicitly.

Alongside it, two tools: get_context_remaining so the model can ask, and new_context_window so it can act. The design position is that context pressure is something the agent should be able to reason about, not something that silently happens to it.

13 · remembering

Persistence, and what is deliberately not persisted

rollout — append-only JSONL

rollout/src/recorder.rs

One .jsonl per session, written by a dedicated task behind an mpsc channel so the turn loop never blocks on disk. A reverse scanner exists so "resume the last session" doesn't read the whole file.

state DB — SQLite

state/

Versioned migrations, log DB, audit trail, telemetry. Backs listing and search across sessions — what a flat log is bad at. The CLI ships a state_db_recovery module, which tells you it has been corrupted in the field.

thread store

thread-store/

The typed API over both, with section-based history reads so a client can page without loading everything.

rollout/src/policy.rs is small and carries a lot of judgment: should_persist_response_item returns false for AdditionalTools, CompactionTrigger and Other — transient control items that would confuse a replay — and persistence is filtered by ThreadHistoryMode so an ephemeral thread can run everything while writing nothing durable. The payoff is fork: 1,959 lines of reconstruction tests exist because replaying a log into an identical live session is genuinely hard.

Config is layered with explicit integer precedence — MDM 0, System 10, Enterprise 15, User 20 (21 with a profile), Project 25, Session flags 30, legacy 40/50. Separately, ConfigRequirements lets a managed layer publish constraints that clamp what higher layers may set, which is why approval_policy is a Constrained<AskForApproval>: an enterprise pins the ceiling even though session flags win on precedence.

14 · the pluggable edges

Five ways to change what the agent does

PreToolUse, PostToolUse, UserPromptSubmit, SessionStart, Stop, SubagentStop, PermissionRequest, PreCompact, PostCompact, Notification.

They are not observers. PreToolUse can return Blocked(reason) or rewrite tool_input — which forces every runtime to be reconstructible from its own hook-facing input, hence with_updated_hook_input and the "stable hook contract" comments in registry.rs. Stop can refuse to end the turn. PermissionRequest can answer an approval without a human. PreCompact can abort a compaction.

Inbound: prewarming, incremental startup events, per-server refresh, elicitations, resources, exposure filtering, skill dependency installation, and lazy start driven by mentions. Outbound: codex mcp-server exposes Codex itself over stdio so another agent can call it as a tool.
Loaded from layered roots, matched by explicit mention or implicit detection. detect_implicit_skill_invocation_for_command watches the commands the agent runs and fires a skill-invocation event when one matches a skill's signature — instrumentation for "the model did this by hand instead of using the skill we wrote."
Manifests, npm sources, bundle archives, marketplace add/remove/upgrade with enterprise source policy, command migration. A plugin ships skills, MCP servers, hooks, and slash commands as one unit — and feeds the discovery loop in §7.

spawn_agent, send_message, followup_task under the collaboration namespace. A spawned agent is a real thread with its own session, optionally forking the parent's history. Two protocol versions coexist with 4,538 lines of tests between them.

One detail worth stealing: ToolCall::direct_source() tags a collaboration call with empty encrypted_function_args as DirectPlaintextMessage, after which the logger prints the literal string "[plaintext arguments]" instead of the content. Inter-agent messages are treated as sensitive at the logging layer, not just at rest.

15 · what the code argues

Ten positions this harness takes

MCP servers reconnect and plugins load asynchronously. Capturing the tool router, MCP binding, environments and AGENTS.md into one immutable StepContext per sampling request eliminates a whole family of races for the price of an Arc clone.
Deferred exposure plus local BM25 search means N MCP tools cost roughly one tool slot instead of N. Discovery is the model's job, and the retrieval is cheap enough — no network, no embeddings, microseconds — that making it a tool call is not a compromise.
The prompt asks for a handoff to another model; the receiving prefix says another model produced it. Framing it that way — rather than "summarise our chat" — produces summaries with decisions, constraints and next steps instead of narration.
Mid-turn compaction must place the summary last because that is what post-training established. Harness and training are coupled through the exact shape of the context window, and the coupling is invisible unless someone writes it down. Here, someone did.
BodyAfterPrefix scoping excludes the cached, stable prefix from the auto-compact budget. Otherwise a session with many tools would compact almost immediately, and the fix everyone reaches for first — raise the limit — silently breaks the sessions with few tools.
Every outward-facing tool goes through ToolOrchestrator::run — the actual path, not a helper you're encouraged to call. That's what makes "no re-approval on escalated retry" and "guardian substitutes for the user" single edits rather than a policy sprinkled across a dozen handlers.
The guardian denies on timeout, malformed JSON, or execution failure — and breaks the circuit after 3 consecutive denials per turn. Both halves matter: the safe default, and the escape from the safe default when it starts costing more than it saves.
A patch confined to writable paths is auto-approved only if a platform sandbox actually exists, because path analysis is defeated by hard links. Where there's no sandbox, ask. Declining to trust your own static analysis is the rare correct call.
A turn ends when the model is done and nothing is queued and no Stop hook wants to continue. Three overrides on the naive condition, each from a real requirement.
Persistent PTYs turn the shell from a request/response tool into a session the agent holds open. That one change forces a process manager, ring buffers, yield tuning, an explicit cleanup Op, and a cap of 64 — and it's the difference between an agent that runs commands and one that uses a computer.
Read it yourself. core/src/session/turn.rs for the loop, tools/orchestrator.rs for the security model, tools/spec_plan.rs for the tool set, and compact.rs + context_window.rs for everything about context. Four files, and the rest is detail hanging off them.
