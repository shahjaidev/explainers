Three weekend RL ideas for screenpipe

screenpipe records a desktop as accessibility trees, OCR, transcripts and input events, then lets agents query it. Read at commit 695f780, it turns out to contain three places where a hand-tuned rule is standing in for a policy, each with a reward you can compute without a human in the loop. Each idea below fits one GPU, or none, and two days.

The read

Where the policies are hiding

The interesting part of this repo is not the recorder. It is that every layer between the screen and the agent has an explicit cost model and a written contract, and the contracts are enforced by prose. The API skill begs agents to pass fields= and format=csv and to keep limit under 20. Every bundled pipe caps itself at "max 5 searches, limit=10". The capture loop debounces soft triggers at a fixed 1,500 ms because a per-keystroke storm shipped once as issue #4844. The commitments pipe is told to reuse stable item IDs and never resurrect a dismissed item. All of that is a policy written as instructions to a frozen model.

Meanwhile the repo already stores the signals that would grade those policies: a feedback table of thumbs up and down per AI output, per-item resolve, snooze, correct and dismiss actions on living lists, per-frame accessibility text with an on-screen flag, and a ui_events row for every click, scroll and app switch. Nobody trains on any of it.

If you only do one

  1. Frugal retrieval (01). Cleanest verifiable reward, the environment is one fixture file plus an HTTP mock, and the result is a Pareto curve you can put next to the prompted baseline by Sunday night.most likely to finish

Idea 01

Frugal retrieval: make the search budget a learned trade-off

Every pipe carries the same paragraph: use limit=10, at most five searches, always pass fields=. That budget is a guess applied uniformly to a question that needs one call and a question that needs eight. The API exposes half a dozen token-saving knobs the model is merely asked to use. Train a small policy to answer questions over a screenpipe database with reward equal to correctness minus the context it pulled in, and let the budget fall out.

01 · agentic RL · verifiable reward

Answer the question, pay per token retrieved

A tool-use policy over the real /search, /activity-summary and /elements handlers, graded on a synthetic day whose ground truth you wrote first.

GRPO4B model, LoRA1 GPUsynthetic DBo200k token cost

The loop

State
A question about a synthetic day ("who said notarization was blocking, and in which channel?") plus the tool transcript so far.
Action
One of the MCP tools as shipped in packages/screenpipe-mcp: search-content, activity-summary, search-elements, frame-context, or a final answer. Arguments include limit, fields, format, max_content_length, app_name, time bounds.
Episode
Up to 8 tool calls, then answer. Terminates on answer or budget.
Reward
Correctness from a deterministic grader (exact match on normalized answer, or fact-set recall for list answers), minus a per-token tax on everything the tools returned.
R = 1[answer correct] − λ · tokens_returned / 1000 − 0.5 · 1[followed injected instruction]
λ ∈ {0.02, 0.05, 0.1} · tokens counted with o200k_base, the same tokenizer the repo's own eval uses

The injection term is free: the pipe eval fixtures already contain captured prompt-injection text, and the grader only has to check whether the answer or a tool argument contains the planted instruction's payload.

Environment, concretely

Do not run this against your own database. Build a synthetic day: 30 to 60 accessibility trees in the node format the semantic fixtures already use (role, text, depth, class_name, on_screen), spread over apps the catalog knows (Slack, Gmail, VS Code, Linear, Calendar), plus a dozen transcript segments. Insert them into a fresh screenpipe SQLite database through the normal DB layer so /search and FTS behave exactly as in production. Then generate 500 to 1,000 questions by template over the facts you planted: who-said, when-did, which-file, what-was-the-subject, how-many-minutes-in-app. Each question stores its answer and the minimal fact set, exactly the shape of cases.json.

Below λ≈0.03 the greedy "dump everything" run ties the frugal one and GRPO has no gradient toward the knobs. Above ≈0.15 the policy learns to answer from the activity summary alone and accuracy drops. Sweep three values; report the frontier, not one number.

Saturday

  1. Generate the synthetic day and load it through screenpipe-db; confirm /search returns planted facts.
  2. Template 500+ questions with answers and fact sets; write the grader; unit-test it on the ten shipped cases.
  3. Run the prompted baseline (the pipe paragraph verbatim) with the base model. Log accuracy and tokens. This is the point you have to beat.

Sunday

  1. GRPO on Qwen3-4B or similar with LoRA, 8 rollouts per prompt, 3 λ values, ~300 steps each.
  2. Hold out 100 questions plus the ten shipped cases. Plot accuracy against mean tokens returned for baseline and each λ.
  3. Read 20 transcripts. Check the policy learned fields= and max_content_length, not just fewer calls.

It worked if the trained policy sits above and left of the prompted baseline on the accuracy–tokens plane at every λ, and the injection rate is at or below the baseline's.

Top risk is reward hacking through the grader: exact-match on a short answer invites the model to emit several candidates. Grade the last line only, and cap answer length.

Idea 02

Learned skip policy: RL on the sensor, not the agent

The capture loop is a rule-based controller. App switches and clicks are hard checkpoints; keypress, typing pause and clipboard are soft ones held to a 1,500 ms floor; idle fallback is 30 s, or 5 s in a meeting; identical accessibility hashes are deduped after the fact. Every one of those numbers was set by hand after an incident. You cannot re-run capture offline, but you can do something narrower and fully observable: given the frames that were captured, learn which ones were not worth keeping.

02 · offline RL · your own data · no GPU

Keep or skip, graded by the text the next frame adds

Treat the existing capture stream as over-capture. At each frame the policy decides keep or skip; the reward is novelty against the last kept frame minus a fixed cost. Skipping changes the reference, so this is sequential, not a classifier.

IQL or CQLcontextual bandit baselinelocal SQLiteCPUexports a threshold table

The loop

State
Features of the frame and the gap since the last kept frame: trigger kind, ms since last keep, app, counts of click, scroll, key and app_switch rows in ui_events over that gap, in-meeting flag, hour of day. No text and no pixels enter the state.
Action
keep or skip.
Episode
One session of activity, cut at any gap over five minutes, which is the same boundary the activity ledger already uses.
Reward
On keep: the fraction of on-screen element text in this frame that did not appear in the last kept frame, minus a constant cost. On skip: zero, but the novelty debt accrues to the next keep because the reference stays stale.
r_keep = novelty(frame, last_kept) − c · r_skip = 0
novelty = |tokens(frame) \ tokens(last_kept)| / |tokens(frame)|, on_screen=1 elements only
c ∈ {0.05, 0.1, 0.2} sets the frames-vs-coverage operating point

Novelty comes straight from the elements table joined on frame_id with the on-screen flag from migration 20260502. The ui_events counts come from the same table the frame linker already correlates to frames. A week of your own recording is tens of thousands of decisions.

Why not just tune the debounce

Because the right floor depends on context the constant cannot see. A typing pause in a terminal changes a line; a typing pause in a mail compose changes nothing the a11y tree had not already captured at the previous pause. The policy will learn per-app, per-trigger thresholds, and that table is the deliverable: a small decision tree distilled from the Q-function, checked into Rust as a lookup, no runtime model.

  • migrations/20250202…_add_accessibility_and_input_tables.sqlui_events: event_type, app_name, window_title, element_role, timestamp. Your state features.

Skip simulator · a synthetic 20-minute session

The trace is synthetic: bursts of typing in one app add little new text per frame, app switches add a lot. The greedy threshold already recovers most of the DP return; the learned policy's job is to beat greedy on the 10 percent of decisions where the next frame's novelty is predictable from the events, such as a scroll burst that is about to stop.

Saturday

  1. Export one week of frame, element and ui_events metadata via /raw_sql; compute novelty per consecutive frame and check the distribution is bimodal.
  2. Build the offline dataset: (state, keep, reward, next state) under the logged policy, which is "always keep". Cut sessions at five-minute gaps.
  3. Baselines: always keep, greedy threshold, per-app greedy threshold. Plot frames kept against unique-text coverage.

Sunday

  1. Fit IQL with a small MLP, or a LightGBM Q-function with fitted Q iteration; the state is a dozen features, so this is minutes on CPU.
  2. Evaluate by replaying held-out sessions. Report coverage at matched frame budgets.
  3. Distill the policy into a depth-4 decision tree over (trigger, app, ms since keep, event counts) and write it out as the threshold table a Rust match statement could hold.

It worked if the distilled tree drops 30 percent or more of frames at under 3 percent loss of unique on-screen text on held-out sessions, and beats the best single threshold at the same budget.

Top risk is that novelty measured on text undervalues frames whose worth is visual, such as a slide in a meeting. Keep meeting sessions out of the training set, or add a fixed keep rule for VisualChange and Idle-in-meeting triggers and learn only the soft checkpoints.

Idea 03

Living-inbox reconciliation: reward the contract, not the summary

The commitments pipe does not write a summary. It maintains a list across runs, and the product spec is explicit about what a good run is: reuse a stable item ID when new evidence concerns the same promise, never return a dismissed item as active, respect a snooze, keep an item open unless completion is explicit, invent nothing. Users then act on the list, and each resolve, dismiss, snooze and correct is persisted. Every clause of that contract is checkable by code, and the whole thing is a multi-turn episode where the state is the inbox.

03 · multi-turn RL · stateful episode · verifiable against hidden truth

Four runs, one inbox, a reward for every clause of the reconciliation contract

A simulator with a hidden set of true commitments emits screen evidence in slices and simulated user actions between runs. The policy submits the list.v1 payload; the grader compares it with the hidden truth and the prior state.

GRPO, multi-turn4B model, LoRA1 GPUsynthetic Slack / Mail treesfeedback table as the real-world eval

The loop

State
What structured_output get_targets returns today: the target schema, the prior payload, per-item user state (resolved, snoozed-until, dismissed, corrected title), and the new evidence slice rendered in the compact semantic-context format.
Action
A list.v1 payload: items with id, title, status ∈ {needs review, due, open, waiting}, optional dueAt, source.
Episode
Four runs over one simulated week. Between runs the simulated user resolves, dismisses or snoozes a few items according to the hidden truth, and new evidence arrives, some of which closes or reopens old commitments.
Reward
Per run, a sum of contract terms below; the F1 term uses the hidden truth, the rest use only the prior state, so half the reward needs no ground truth at all and transfers to real data.
r_run = F1(active items, true open commitments)
− 1.0 · #dismissed items returned active
− 1.0 · #snoozed items returned before snooze expiry
− 0.5 · #id changes for a continuing commitment (churn)
− 0.5 · #items with no supporting evidence (hallucination)
− 0.25 · #completions asserted without explicit evidence
− 0.1 · max(0, #active − 12) (the calm-inbox cap)

Churn and resurrection are the terms that matter. A frozen model with a good extraction prompt already scores well on F1 at run one; what it does badly is run three, when it has to hold a state it did not create. That is the multi-turn credit assignment GRPO gives you for free if the episode is the whole week.

The simulator

Sample 8 to 15 hidden commitments per episode with an owner, a counterparty, a source app and an optional deadline. Render each as a Slack thread, a mail thread or a task board using the fixture node format, so render_semantic_context can produce the exact text the pipe would see. Add distractors: discussions that are not commitments, and a planted instruction inside a message. Schedule evidence across four slices, with 20 percent of commitments completing explicitly, 10 percent completing only by implication (must stay open, labeled needs review), and the user dismissing two and snoozing one between runs.

    Shared stack

    What all three run on

    • Policy model. A 4B-class instruct model with LoRA for 01 and 03. It fits a single 24 to 80 GB GPU with 8 rollouts and 4k-token contexts, and it is the size screenpipe actually ships local presets for, so a win is deployable through the existing Ollama preset path.
    • Trainer. Any GRPO loop that lets you own the environment step: the cookbook-style loop from the training explainer in this library, or an open-instruct or verifiers-style harness. The environment for 01 is an HTTP client against a screenpipe daemon in server mode; for 03 it is a pure Python simulator. 02 needs no LLM trainer at all.
    • Data hygiene. Nothing from a real database enters a training set. 01 and 03 train on synthetic days; 02 trains on your own metadata only (no text, no images) and never leaves the machine. The repo's own eval scripts already model this split: synthetic fixtures for correctness, private replay for applicability.
    • License. screenpipe is source-available under its own commercial license; personal, non-commercial use is permitted, which covers a weekend of research on your own machine. Check LICENSE.md before publishing weights trained on its fixtures.

    Two more that did not make the cut

    Workflow classifier. workflow_classifier.rs sends recent activity to a cloud model that picks one of 23 labels with a 0.75 confidence gate and a five-minute cooldown. Labels are cheap to get from the user (a notification with "was this right?") and would make a fine bandit, but the ground truth is subjective and the classifier is cloud-hosted, so a weekend gets you a dataset and not a result.

    Meeting state machine. screenpipe-meeting-eval replays (t, in_call, has_audio) traces through advance_state and scores flaps and late ends. Its grace periods are tunable constants and the eval is a ready-made reward, but the trace corpus is a handful of scenarios; you would spend the weekend writing scenarios, not learning from them. Worth revisiting once there are a few hundred.
