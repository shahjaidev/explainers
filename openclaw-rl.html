Gen-Verse · arXiv 2603.10165 · Apache 2.0

Every reply you send back is already a label.

OpenClaw-RL wraps a self-hosted model in an OpenAI-compatible proxy, watches your ordinary multi-turn conversations go by, and turns whatever happens next — your follow-up, a test verdict, a stack trace — into the training signal for the turn that came before. Nothing is labeled by hand. Nothing blocks. The model keeps serving while it learns.

Conventional RLHF stacks collect a dataset, stop, train, then redeploy. OpenClaw-RL decouples agent serving, rollout collection, PRM/judge evaluation, and policy training into four independent async loops. A slow judge never stalls the model you are talking to; a training step never drops a request on the floor.

The central idea

One next state, two different kinds of supervision

When you reply to an agent, your message carries two separable things. It carries a verdict — that answer was good, or it wasn't — and sometimes it carries a correction: the specific thing the agent should have known. OpenClaw-RL extracts both, and they have opposite statistical shapes.

Evaluative · dense · scalar

The PRM vote

A process reward model reads (response, next_state) and returns +1, -1, or 0, majority-voted over PRM_M independent samples. Almost every scored turn produces one — even when the feedback is implicit, like you re-asking the question or a test simply passing. One number for the whole response.

Directive · sparse · per-token

The hindsight hint

When the next state actually contains a correction, the judge extracts it as a hint wrapped in [HINT_START]…[HINT_END]. Replaying the same response through a hint-conditioned teacher yields a log-probability gap at every single token — far richer than a scalar, but only available on the minority of turns that teach something.

Binary RL uses only the left column. OPD uses only the right. The hybrid recipe — the one the repo's headline command runs — sums both losses per token, and reports stronger, more stable optimization than either alone. Everything below is a consequence of this split.

Three learning paradigms

Shared loss shape

      

        Every method lands in the same PPO-style clipped objective with asymmetric clipping —
        eps-clip 0.2 on the low side, eps-clip-high 0.28 on the high side,
        which lets the policy move up faster than it moves down. Rewards are deliberately
        not normalized (--disable-rewards-normalization), because a
        ±1 PRM vote is already on a meaningful scale. A KL term against the reference
        policy keeps it from drifting: βKL = 0.02 in Binary RL,
        0.0 in the default OPD launcher. Entropy bonus is off everywhere.
      

    

  










  

    

      
Anatomy of one trainable turn

      
From your reply to a gradient, step by step

      

        This is the OPD path, which is the more involved of the two. Each stage happens on its own
        async loop — by the time step 5 runs for one turn, step 1 has already run several times for
        later turns in the same session.
      

    


    

      

        

        

      

    


    

      
Which turns are even eligible

      

        Not every API call is training data, and the framework is careful about this. The OpenClaw
        extension stamps two headers on every outgoing request:
        X-Session-Id groups turns into a session, and X-Turn-Type marks a
        turn main (you actually asked for something) or side
        (a heartbeat, memory flush, or cron job). Only main-line turns train.
      

      

        A turn also needs a next state to be scored against — so the final turn of a session normally
        gets loss_mask = 0 and is dropped. The exception is the
        at-least-one guarantee: if every turn in a session scores ≤ 0,
        the best turn is promoted to reward +1 so the session still contributes a
        positive example rather than pure negative gradient.
      

    

  










  

    

      
The refinement that matters most

      
A good hint is one the student could plausibly have followed

      

        Naive OPD has a failure mode: the hint-conditioned teacher may produce a distribution the
        student policy has essentially zero mass on. Distilling toward it is a large, noisy update
        that teaches nothing transferable. The topk_select path fixes this by generating
        several candidate hints and picking the one whose teacher distribution the student
        already overlaps with.
      

      

        For each candidate hint h and each response position i, it compares
        the student's top-k vocabulary against the hint-conditioned teacher's top-k, and counts the
        intersection. Drag the slider to see how overlap separates candidates.

Selection rule · OPENCLAW_TOPK_HINT_SELECTION

        

          

            
              
sequence_optimalOne hint per sample, maximizing summed overlap across all response tokens. Default, and the more stable choice for agentic RL.

              
token_optimalBest hint chosen independently at every token position. Higher ceiling, noisier.

              
shortestFirst candidate after the server sorts by hint length. A cheap baseline.

            
          

        

      

      

        
Vocabulary subset · OPENCLAW_TOPK_SUBSET_MODE

        

          

            
              
studentDistill only over top-k(πold). Default — keeps the update inside what the policy already considers.

              
teacherUse top-k(πT) from the selected teacher instead.

              
overlapIntersection of both sets. Most conservative, smallest effective update.

            
          

        

      

    


    

      

        Option B — top-K logits distillation (SDFT / SDPO lineage)
        

          

            A parallel branch in openclaw-opd/, contributed alongside the authors of
            SDFT and
            SDPO. Instead of a single teacher target per
            token, it distills the teacher's full top-K distribution per position, with a reverse-KL loss
            over K+1 bins — the K explicit tokens plus one tail bin absorbing the remaining
            mass, computed as log(1 − exp(logsumexp(log p₁…log p_K))).
          

          

            Note the deviation the README flags explicitly: this implementation uses the
            teacher's top-K rather than the student's, unlike the original papers. That's an open
            comparison, tracked in issue #7.
          

          

            It is deliberately built as a strictly additive extension — the legacy token-level path is
            untouched, teacher_log_probs [T] keeps its original meaning, top-K lives in
            separate teacher_topk_log_probs / teacher_topk_indices fields, the
            loss is external rather than a core switch, and the whole thing is off by default at
            --distill-topk 0.
          

          
cd slime
bash ../openclaw-opd/run_qwen3_4b_openclaw_opd_topk.sh

# equivalent key args
--loss-type custom_loss \
--custom-loss-function-path topk_distillation_loss.topk_distillation_loss_function \
--distill-topk 50 \
--disable-compute-advantages-and-returns \
--entropy-coef 0.00

        

      

    

  










  

    

      
Deployment shape

      
One node has to hold four different models at once

      

        This is the part that surprises people. A single OpenClaw-RL run is not just a policy — it is
        a policy being trained, the same policy being served, a PRM judge, and (in the hybrid path) a
        teacher. Every launcher partitions the node explicitly, and asserts the split fits before it
        starts Ray.

        Tinker (LoRA-only, cheap, one run.py entry point for all three
        methods) and Fireworks (full-parameter or LoRA, private-preview SDK). In both
        cases only a local FastAPI proxy runs on your machine.

        The evaluation nobody expected — everyone in the loop is using AI
        

          

            openclaw-test/ is a three-phase end-to-end eval built on GSM8K, and the setup is
            a small joke with a serious point. A student LLM asks the agent to do its
            homework — and if the answer looks too AI-generated (bold text, numbered lists), tells it to
            rewrite in a more natural voice. A TA LLM then grades those same submissions,
            pushing back when comments are too brief. Finally a teacher LLM reviews the
            graded work and demands friendlier, more patient feedback.
          

          

            Each phase exercises a different bundle of skills — file I/O and style adaptation, then
            evaluation accuracy and feedback specificity, then tone control — and each is driven entirely
            by natural rejections rather than a rubric. Run order matters:
            student_chat.py → TA_chat.py → teacher_chat.py, since
            each phase consumes the files the previous one wrote.
          

          

            The point is that a single personalized model has to satisfy three users with directly
            conflicting preferences, all discovered from conversation alone.

Before you point this at your real work

      
Honest edges

      

        Your conversations are training data. The repo's own reminder is the right
        one: don't feed sensitive personal information into a model that is recording every turn to
        disk, and keep API keys out of prompts and logs. Records land in
        <method>/results/*.jsonl whenever OPENCLAW_RECORD_ENABLED=1,
        which is the default in the shipped launchers.
      

      

        The judge is the same class of model as the policy. The PRM defaults to the
        same checkpoint family being trained. Majority voting over PRM_M samples
        mitigates variance, not shared bias — a mistake the policy is prone to is one the judge may
        well endorse.
      

      

        Some knobs are open questions, not settled defaults. Teacher top-K versus
        student top-K is explicitly unresolved (issue #7). The at-least-one guarantee is a pragmatic
        floor against all-negative sessions, not a principled estimator. Treat the defaults as the
        authors' current best guess.
