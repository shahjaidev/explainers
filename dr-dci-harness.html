Three tools, one growing folder

DR-DCI gives a search agent almost nothing: a retrieval call, a shell, and a file reader. The whole method is what happens between them — retrieval pulls documents out of a hidden corpus into a local directory, and the agent greps that directory like a codebase.

Lu, Li, Nie et al. · 2026 github.com/EigenTom/DR-DCI BrowseComp-Plus 71.2% · $34.91
The problem it fixes

Ranked snippets are too thin; a 10M-file corpus is too slow

Two ways to let an agent search a corpus, both broken at the ends.

Classic RAG hands the agent a top-k list of snippets. That scales to any corpus size, but the agent can only read what the ranker chose to show — it can't reorganize evidence, cross-check a constraint across three documents, or rule out a near-miss. In the paper's own baseline, snippet-only BM25 lands far below every agentic variant.

Raw Direct Corpus Interaction goes the other way: mount the whole corpus and let the agent run rg over it. Precision is excellent — until the corpus grows. Past a few hundred thousand documents, corpus-wide grep calls start hitting the 30-second tool timeout and flooding context with irrelevant matches. The failure is operational, not cognitive: Raw-DCI averages 3,139 seconds and $88 per query and becomes infeasible to even measure at 10M docs.

DR-DCI's move is to keep both halves and separate their jobs. Retrieval does discovery over the hidden corpus. The shell does verification over a bounded local workspace. The agent decides when to switch.

The action space

Everything the agent can do

The main run is launched with --tools read,bash,pull. That is the complete list — no web access, no sub-agents, no memory store.

pullcorpus → workspace

The only tool that can see the hidden corpus. It retrieves, drops anything already visible, hard-links the rest into the workspace, and returns a compact ranked preview — a navigation hint, not evidence.

pull(query, topK) → ΔW, ranked preview, stats
  • topK 300–600, one query per call
  • Qwen3-Embedding-8B over FAISS, port 8002
  • Hard links, never copies
  • Preview mode: ranked / shuffled / hidden
bashinter-document

A sandboxed shell over the materialized folder — rg, grep, find, ls. This is where the agent combines constraints, follows bridge entities, and kills false positives.

rg "husbandry" . -l find . -name "*aquarium*"
  • 30s timeout, network blocked
  • Output capped: last 2000 lines / 10KB
  • Long lines clipped to 2000 chars
  • Truncation emits a resumable read={…}
readintra-document

Bounded file reading with two window modes. Line windows for normal files; character windows for the OCR-mangled single-line documents that make rg return a whole page as one match.

read(path, offset, limit) read(path, charOffset, charLimit)
  • Default char window 4096
  • Every clip reports the next offset
  • Parallel execution enabled with bash
  • Never asked to read a whole document
Environment engineering

The unglamorous half

Most of the harness is defenses against ways a shell agent quietly fails. Each of these is a specific bug they hit and fixed.

Root-flat workspacewas: pull_1/, pull_2/

Early versions gave each pull its own folder. The agent then had to guess which folder to search, and paths encoded retrieval rank — brittle and easy to mistype. The shipped version dumps everything into one deduplicated root and discloses rank in the tool response instead of the path.

Their ablation found rank-aware folders can raise raw recall while lowering final accuracy. Recall the agent can't navigate is not recall.

Shell-safe filename slugsspaces, quotes, unicode

Document titles contain spaces, colons, quotes, and non-normalized Unicode — all of which break naive shell quoting. Filenames are normalized to stable slugs while titles, URLs, retrieval rank, and provenance are preserved in metadata.

Selective reflow of single-line fileswidth 1200

PDF and OCR extraction often yields a document that is one enormous line. A single rg match then returns the entire page. At materialization time, files with two or more lines are hard-linked untouched; pathological single-line files are reflowed at 1200 characters. Normal long lines are not globally hard-wrapped.

Truncation that hands back a next stepcontinuation hints

Truncation without a way to resume just loses evidence. Every clipped output ships with an executable continuation — the agent is told exactly which call reads the next window.

[path]:[line]: ...snippet... [long line clipped; term="..."; lineChars=12345; read={"path":"...","charOffset":3200,"charLimit":1600}]

And for line-oriented reads: [Showing lines 1-123 of 999. Use offset=124 to continue.] The prompt explicitly instructs the agent to follow these hints rather than re-reading the file.

Context management, level 3300 turns

A 300-turn trajectory over grep output will blow any context window. The harness ships six preset profiles; the main runs use L3 — tool results truncated at 20K chars, micro-compaction on keeping the last 12 turns, and in-loop compaction off.

Workspace-preserving context resetoptional · 49 / 830 queries

The one mechanism that isn't part of the core interface. When a finished trajectory reports confidence ≤ 70 and explicitly abstains, the harness throws away the entire reasoning history but keeps the materialized folder, then runs a fresh agent over it.

The insight: retrieval state and reasoning state fail independently. A trajectory can talk itself into a dead end while sitting on a directory that already contains the answer. Fires on 49 of 830 queries and moves accuracy from 71.2% to 73.3%. The deliberately narrow trigger keeps it from degenerating into a retry loop.

Evidence

Which parts actually carry the result

Three controlled ablations on a 100-question subset. Each one removes a single interface property and holds everything else fixed — which is what makes them worth reading.

Should retrieval be a preprocessing step or an agent action?

accuracy /100
dynamic pull82
single pull, frozen79

A modest accuracy gap — but dynamic pull got there with fewer tool calls, 104s instead of 172s, and $3.44 instead of $8.83. The win isn't a bigger candidate set; it's letting failed local searches decide when to retrieve again.

Does the ranked preview do real work?

accuracy /100
ranked top-2082
shuffled top-2076
hidden (stats only)72

The three-way split separates two effects: naming candidate files at all is worth ~4 points (hidden → shuffled), and ordering them correctly is worth another ~6. Same documents on disk in all three.

Is cross-document shell search load-bearing?

accuracy /100
full tools82
inter-doc DCI blocked40

The decisive one. Keep the ranked preview, block recursive rg/find across files, and accuracy halves. The agent compensates by pulling 20.5 times per query instead of 3.5, dragging in 3,022 candidates instead of 995 — and still fails. More retrieval does not substitute for being able to search what you retrieved.

Scaling

The workspace stays small while the corpus doesn't

Distractor documents added to BrowseComp-Plus, 100K → 10M. The point isn't that accuracy holds — it's why it holds.

Across a 100× corpus increase, DR-DCI's materialized workspace stayed bounded at roughly 1,000–1,400 documents, tool errors stayed low, and total cost stayed around $4–$5. The agent never sees more of the corpus as the corpus grows — retrieval absorbs the scale, and the shell keeps operating on a folder it can actually finish grepping.

Raw-DCI fails in the opposite direction, and not because it reasons worse: its shell commands hit the 30-second timeout more and more often until evaluation stops being feasible. BM25 never breaks, and never gets good.

Reproduction

The actual main run

Every claim above comes from this configuration, verbatim from run_full830_dynamic_pull_root_flat_openai_high_l3_300turn_parallel30.sh.

# retriever must already be up on :8002 --model gpt-5.4-nano --pi-thinking-level high --tools read,bash,pull --max-turns 300 --max-concurrency 30 --runtime-context-level level3 --pull-view-mode hardlink --pull-layout root --pull-materialization-mode root_flat_disclosed --pull-prompt-mode rank_aware --pull-min-top-k 300 --pull-max-top-k 600 --pull-max-queries 1 # environment knobs DCI_BASH_DEFAULT_TIMEOUT_SECONDS=30 DCI_BASH_MAX_LINE_CHARS=2000 DCI_REFLOW_SINGLE_LINE_WIDTH=1200 DCI_WRAP_LONG_TEXT_LINES=0

One discrepancy worth knowing if you run it: the paper describes pull(query, topK) with topK 300–600, but the underlying TypeScript schema in pull.ts accepts a queries array of up to 8 with topK 100–500. The launch script reconciles them with --pull-max-queries 1 and min/max overrides.
