Fireworks AI · training cookbook

You write the training loop. They run the trainer.

The cookbook is a set of ready-to-fork Python training loops — reinforcement learning, preference optimization, supervised fine-tuning, distillation, embeddings — that run against Fireworks' hosted trainers over a Tinker-compatible API. There is no framework to learn and nothing to subclass. Every recipe is a single readable file where the loss, the reward, and the rollout are ordinary Python you own.

Apache-2.0 Python ≥ 3.11 8 recipes 9 RL objectives LoRA & full fine-tune Tinker-compatible

Your code

  • the reward function
  • the rollout / environment
  • the loss, if you need a custom one
  • batching, filtering, per-step logic
  • when to checkpoint and promote

Fireworks' side

  • the trainer job and its GPUs
  • the inference deployment
  • weight sync / hot-loading
  • checkpoint storage and promotion
  • train↔inference numerical alignment

The boundary is the product. Most RL frameworks hand you a config file and take the loop away. This hands you the loop and takes the infrastructure away — which is why every recipe is a few hundred lines you can read end to end, and why swapping GRPO for GSPO is a one-line import change rather than a framework fork.

Policy objectives

      
The RL loss menu

      

        Nine shipped objectives, one module each in utils/rl/, every one a
        make_*_loss_fn builder you pass to forward_backward_custom.
        There is deliberately no registry and no runtime dispatch — you switch objectives
        by changing an import in your fork, which keeps the gradient path readable.
      

    


    

      
      
      
      
      
    

    


    

      TIS is the one you compose, not choose. Train-inference importance sampling corrects
      for the numerical gap between the training kernel and the inference kernel that generated
      the rollouts. It multiplies into any of the policy losses above, and it is the mechanism
      behind the claim that training and serving stay aligned.

training/examples/

      
…and the worked examples that use them

    

    

      

        Serverless RL — Countdown
        

          
The example from the K3 blog post, and the shortest path to a running RL job. GRPO on the
          Countdown numbers game with nothing provisioned. Three files: the loop, a vendored reward, and
          32 sample rows so it runs out of the box.

          
The reward is deliberately dense so the policy can climb from cold: +0.1 for emitting a
          parseable <answer>, +0.2 for using exactly the source numbers,
          +0.7 for hitting the target.

        

      

      

        Coding agent — SWE-Gym
        

          
Black-box agent RL: an unmodified claude-code CLI is pointed at a shim that
          translates Anthropic's /v1/messages to Fireworks, runs against local SWE-bench Docker
          images, and is graded by the SWE-Bench harness. Trains through async_rl_loop.

          
The point it proves: the rollout can be an opaque third-party binary, because the cookbook only
          needs tokens and a scalar back.

        

      

      

        Multi-hop QA — IGPO on HotpotQA
        

          
The model calls search(query) then submit_answer(answer). Instead of one
          sparse end reward, each turn is credited with how much it raised the log-probability of the true
          answer: r_t = r_env + ig_weight · [log P(a|p_t) − log P(a|p_t−1)]. Scoring runs on the
          inference deployment, in parallel with generation.

        

      

      

        Frozen Lake, DeepMath, GSM8K
        

          
Frozen Lake — multi-turn tool-calling GRPO where Eval Protocol owns the data plane and the
          cookbook owns training. DeepMath — GRPO on probability problems with a math-verify reward.
          GSM8K multi-turn — a port of AReaL's multi-turn math example, with loss masks kept aligned
          across a retry turn so only assistant tokens train.

        

      

      

        Distillation, SFT, DPO, ORPO, embeddings
        

          
Privileged-context distillation on GSM8K (the teacher sees context the student doesn't), routed
          two-teacher distillation, text2sql SFT, a vision-language SFT variant, IFEval ORPO, and retrieval
          pairs. Plus six runnable case-study notebooks: prompt routing, receipt vision SFT, style DPO,
          reasoning RFT, support-search embeddings, and a multi-LoRA serving fleet across 51 locales.

        

      

    

  


  
  

    

      
The unglamorous load-bearing part

      
Renderers, and why they decide whether training works

    

    

      
A renderer turns chat messages and tool definitions into the exact token sequence a
      given model expects, plus a per-token loss weight — and parses generated tokens back into
      a message. Get it subtly wrong and nothing crashes; your rewards are just quietly computed
      on mis-decoded text, and the run silently learns the wrong thing.

      
This is where the repo does its least visible and most valuable work. Kimi K3, for instance,
      ships no Jinja chat template at all — the format lives in Python helpers inside the
      tokenizer, so the cookbook's renderer resolves and calls those directly. For SFT it trains the
      assistant body through <|close|>…<|sep|> and pins the following
      delimiter at weight zero.

      
A second class of renderers exists purely to fix upstream ones: the _*_split
      modules subclass models whose chat templates strip historical reasoning, so that multi-turn
      SFT on every assistant message actually works.

Also in the box

      
Supporting machinery

    

    

      

        Checkpoints, LoRA merging, promotion
        

          
Checkpointing collapses to two independent flags on one call: resumable=True
          writes weights and optimizer state; promotable=True writes an HF
          safetensors snapshot eligible for promotion to a served model. The control plane is the
          source of truth — the only local file maps checkpoint names to how much data was consumed.

          
The two snapshot types are not interchangeable, and the trainer rejects the mix-up
          explicitly rather than failing later. Standalone tools cover promoting from a dead trainer,
          listing checkpoints, and merging a LoRA adapter back into its base to promote a full model.

        

      

      

        Weight sync and hot-loading
        

          
After each optimizer step, new weights have to reach the inference deployment. Two ownership
          models: PER_TRAINER (default — the deployment follows the trainer's bucket, and a
          resume briefly restarts the serving pod) and PER_DEPLOYMENT (a stable
          deployment-scoped bucket, no restart on resume, but pinned to one deployment).

          
Transitions are ASYNC (pause mid-flight, resume on new weights, reuse the KV
          cache) or SYNC (drain in-flight requests so no generation ever spans two policy
          versions, at the cost of a stall). Mixing the two ownership scopes on one pair was historically
          the top source of hot-load failures; the server now rejects it at creation time.

        

      

      

        The agent skill
        

          
A single installable skill (skills/fireworks-training/, plus 27 progressive
          reference docs) that lets a coding agent drive the whole workflow. Notable for its guardrails
          rather than its capabilities: firectl blocks mutating commands when it detects
          Claude Code, Cursor, or Codex, and the skill is forbidden from working around that — it surfaces
          the command for a human to run.

          
It also mandates a 14-item confirmed plan before anything is uploaded, created, promoted, or
          billed, and fixes a source-precedence order so an agent never answers pricing or shape questions
          from memory.

        

      

      

        Evaluation, and the advisor
        

          
eval/ carries HealthBench Professional adapted to Harbor — pinned to an exact
          dataset revision and SHA-256, failing loudly on any mismatch — and a multi-LoRA hot-reload eval.

          
advisor/ is unrelated to training and worth knowing about anyway: a critique-only
          reviewer where an open-source worker model does the coding and a frontier model reads the working
          git diff and returns scored issues. It cannot edit files.

        

      

      

        What you can safely ignore
        

          
The repo's own CLAUDE.md is blunt: only training/ matters.
          archived/ holds the previous generation of the cookbook — RAG walkthroughs, integration
          demos, legacy recipes — and is not maintained against the current SDK.

        

      

    

  


  
  

    

      
Getting going

      
Fifteen minutes to a reward curve

    

    
# the --pre matters: without it you resolve to the stable 0.x line,
# which has no managed training SDK clients
git clone https://github.com/fw-ai/cookbook.git
cd cookbook/training
uv venv --python 3.12 && uv pip install --pre -e .

export FIREWORKS_API_KEY=fw_...
python -m examples.serverless_rl.countdown_rl

    

      That writes metrics.jsonl and a reward curve to a fresh run directory. The defaults
      are a real training run, not a smoke test — drop steps, group_size, or
      max_sample_tokens first if you only want to prove the wiring works. And if you point
      it at a different base model, change tokenizer_model to match: a mismatch doesn't
      error, it corrupts your rewards.
