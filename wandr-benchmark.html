01 The task shape

A task is a tree of quotas that bottoms out in URLs.

Most research benchmarks pick one of two shapes: find one hard answer (BrowseComp, GAIA), or write one long report (DRACO). WANDR picks a third: return a structured collection, where discovery and per-item depth multiply.

The representation is a qualification key hierarchy. Each level names a kind of item; each edge means for each parent, find this many children; every branch terminates in a url. The counts are per parent, not global — that single detail is what makes the tasks expensive.

RUNNING EXAMPLE — ceo_cfo_appointments
company(70) → company_appointee{company, appointee}(1) → url(1)
subtask company(70) → url(1) — listing-authority evidence, same companies

“For at least 70 US-based companies, find a CEO or CFO appointment first announced in March–April 2026, cite an authoritative announcement page — and separately prove each company's US exchange listing.” 140 records. The composite key {company, appointee} exists so the same person appointed at two companies doesn't collapse into one entity.

One record = one root-to-leaf path

{"item":    {"company":"...","appointee":"..."},
 "url":     "https://...",
 "excerpts":["verbatim quote", "..."],
 "answer":  { ...free-form claim fields... }}

The record is the atomic unit of grading. item carries the identifying keys, url the page, excerpts the proof, answer the claim. Everything the task asks must be visible inside the excerpts — not merely nearby on the page.

Wide × deep, quantified

Across the released set the medians are 100 members, 3.00 records per member, 245 records per task. Breadth and depth are separately dialled: 18.4% of tasks need under 50 members, 16.6% need 200+; 21.6% need a single record per member, 3.4% need ten or more.

A flat list and a fixed-schema table are both special cases of the hierarchy — 13% of tasks are flat, the rest add one or more intermediate key levels.

02 Structural variations

Six ways to bend the tree.

Changing what a level represents, how many children it demands, or where a branch attaches covers a surprising range of real workflows without inventing a new output format each time.

Flat list

One entity level over URL leaves. company(n)→url(1).

Nesting

Containment: countries → cities → evidence.

Fan-out

Related-but-not-contained children: a quote fans out to attributed authors.

Dispatch

A fixed label set instead of discovered entities — forces facet coverage.

Corroboration

Two independent pages must each satisfy the whole claim.

Matrix

The same child set repeated under every parent — every model × every benchmark.

Anchors and partitions do quiet work. An anchor is a count-one intermediate key that binds downstream children to one selected value: in company(n)→product(1)→distributor(2) both distributors must refer to the same product. Flatten it and you lose the guarantee. A partition — country(3)→company(m) — forces geographic spread a flat list would never produce. Subtasks reuse a parent key and attach a whole second hierarchy: another source family, another angle, or a chain into a further entity.

04 Grading a record

No answer key. The grader re-reads your sources.

This is the design choice that makes the rest possible. There is no gold collection to match against — so tasks can be about current, changing facts, and task production can scale without exhaustive expert annotation. In exchange, grading inherits fetch and judge uncertainty, and a page that drifts between solving and grading can fail an otherwise correct record.

Every leaf verdict is a product of binary checks. Not a rubric score — a conjunction. One zero anywhere and the record is worth nothing.

UNIVERSAL BLOCK — same for every task
TASK-SPECIFIC BLOCK

The judge also emits a confidence. Leaves below confidence 2 are treated as missing: they never enter precision, but their absence can still starve recall.

verdict_full grades the whole submitted record — the page and your excerpts. It is the headline metric.

verdict_retrieval asks only whether the fetched page satisfies every substantive requirement, ignoring how well you quoted it. The gap between them is the cost of evidence rendering — how much credit you lose to excerpt selection rather than to search.

Stage 1

Solve

Any system, normalized into one record format so grading is identical across providers.

Stage 2

Fetch

Re-fetch every cited page. Triage routes bot-walls and JS-only pages to a heavier browser — fail on evidence, not on our crawler.

Stage 3

Judge

Canonicalize closed key axes, semantically dedupe open ones, then one structured verdict per record.

Stage 4

Score

Bottom-up rollup into soft and hard precision, recall, F1 — per task.

05 The rollup

Why hard F1 collapses to a third of soft F1.

One universal aggregation, parameterized on two axes. Precision averages every supplied child. Recall first collapses duplicate identities by taking the worst score per entity, sorts what remains descending, keeps the top k where k is the required count, and zero-pads any shortfall. Soft passes the aggregate through; hard thresholds it at exactly 1.0 at every level except the root — so only fully-qualified subtrees propagate.

Where the gaps come from

  • Precision → recall is mostly a breadth signal. Recall zero-pads unmet quota; precision only averages what you handed in. Submit three perfect members out of seventy and precision is 1.0 while recall is 0.04.
  • Soft → hard is a completeness signal. It removes all partial credit from members whose required subtree isn't finished.
  • Full → retrieval is an evidence-rendering signal: found the right page, quoted it incompletely.

Composition, and the equal-weight convention

A subtask that shares a parent key multiplies into the parent entity's score — a weak listing branch drags down an otherwise perfect appointment record. A dispatch fan-out is averaged instead: three of four evidence families is 0.75. And the benchmark headline is a plain unweighted mean over tasks, so a 30-record task counts exactly as much as a 2,750-record one.

07 Failure anatomy

The bottleneck is not search. It is proof.

Solving a WANDR task is executing a retrieval program: discover enough members, enrich every branch, qualify the pages, render source-backed records. The score tree lets you localize which of those four stages ate the credit.

FULL SOFT RECALL DECOMPOSED — share of total loss per stage

Extraction removes 31–73% of whatever score reaches it, yet it is the smallest contributor for five of six systems — because discovery and enrichment have already destroyed 48–89% of the opportunity. OpenAI is the clean counterexample: it retains 83.9% through discovery and then loses 68.2% of the remainder in enrichment.

Read it left to right. Fetching a usable, broadly in-scope page is nearly solved — 3–9% failure for five systems. Then it falls apart: 34–68% of records cite a page that doesn't actually satisfy every substantive requirement, and the excerpt bar is harsher still.

Partial proof is the signature failure

Condition on records where the fetched page does satisfy everything, and where the excerpts are faithful. Those excerpts support at least one requirement 97–99% of the time — and all requirements only 56–80% of the time.

SystemFaithfulAny supportedAll supported

The gap widens with more required checks (−7 to −22 points from 2 checks to 5) and with longer source pages, in five of six systems.

Scale hurts in two different ways

  • Target volume erodes mostly before extraction. From the smallest to largest volume bin, retrieval-only hard recall falls 0.376 → 0.172 (Perplexity), 0.267 → 0.117 (Anthropic), 0.191 → 0.056 (OpenAI).
  • Hierarchy depth hurts everything. From flat to 3+ levels, Perplexity's retrieval-only hard precision falls 0.578 → 0.105 and recall 0.523 → 0.072. Averaged across systems that's −34 and −35 points.
  • Identity collapse is rare but sharp: only 2.4–8.0% of tasks contain a merged duplicate, costing 0.02–0.13 points of soft recall on average — but 0.8–4.5 points on the tasks it touches.
Volume collapse
Incomplete query decomposition and insufficient retrieval at scale, sometimes followed by hallucinated values to fill the quota. Recall zero-padding makes this expensive; hallucination then also costs precision.
Snippet reliance
Using a search-result snippet without opening the source to check that it supports the submitted claim. Shows up as page req. unmet or unfaithful excerpts.
Non-systematic constraint application
Applying the eligibility filter to the first few entities and silently dropping it thereafter — precision decays with position in the output.
Cross-reference skips & missing enrichment
Asserting a claim without corroborating it across the required sources; or finding an entity and never gathering its required facts. Both are hard-metric killers: the member's subtree never completes, so it contributes zero to every hard score.
Premature stopping & context overflow
Giving up after an initial search returns too little, or exhausting context on a long trajectory. These are why the paper argues wide research is a systems problem — state persistence, quota tracking, and backfilling matter as much as the model.

09 Before you cite it

Caveats that change the reading.

The grader shares infrastructure with one contestant

Cited pages are re-fetched through an agentic fetch backend that is also available to the Perplexity solver. The authors say so plainly: the grading path may be better aligned with pages the Perplexity solver can reach. Internal ablations that disable it lower every system's score while leaving the ranking mostly stable — so absolute numbers are affected, ordering apparently less so. It's a disclosed structural conflict, not a hidden one, but it belongs in any citation.

One run per system, no variance

The main table is a single production run per endpoint. Systems differ simultaneously in model, search infrastructure, agent harness, tool interface and provider implementation — so the ranking is observational and isolates no component. An earlier, separately configured evaluation reproduced the same ordering, also without repeated trials.

Reference-free grading has its own error bars

No gold table means no annotation bottleneck — and also LLM-judge error, page drift between solving and grading, extraction gaps on dynamic or JS-rendered content, and canonicalization boundary calls on ambiguous identities. The judge audit blocks a task if the automated judge's error rate exceeds roughly 10% of a hand-regraded sample, which bounds but does not eliminate this.

The task set is deliberately not representative

Admission favors high-volume, feasible, discriminative tasks with independently verifiable web evidence. It's a stress test, engineered so that primitive baselines score near zero and stronger systems separate. Don't read 0.363 soft F1 as "research agents fail 64% of real requests."

If you're building on it: the released split is an evaluation set. The paper's own RL section says training should use generated sibling tasks or newly generated tasks from held-out seeds — and should test explicitly for reward hacking via over-submission, evidence templating, and exploitation of judge or cache artifacts.
